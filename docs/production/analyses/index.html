Analyses

Configuration vs reality, across both logs: which configured names are actually seen, and what belongs together.

Coverage & seen
Entity coveragePer account, partner, domain or application: does each configured direction actually work — proven by real transferred Files, successful SSH logons (In) or successful UC3 remote polls (Out).
First seenOn what day each logical flow, partner, subscription, account, login and remote host was first seen in the transfer logs — the configured names never seen there on top; every count links its item list.
Since yesterdayThe data diff against the newest log day: new red flips, flows that just crossed the quiet threshold, recoveries, first-seen entities by name and new server-log-only names.
File searchFind a File by its file name — date, subscription, size and CoreId, OK rows green and Error rows red; six windows (24 hours through a month), each searched with its own Search button and the query carried between them.
Seen in server logThe entities that appear in the SERVER log only (blue): their seed messages, what happened, and the status rollups with the blue deltas.
Configuration
Use casesThe configured subscriptions grouped by their UC<n> prefix — Total, Server (server-log only), Not seen, Error and OK per use case; tabs for the Use Case definitions (who connects, which way the file travels, what triggers it) and the Use Case patterns (the accounts grouped by their subscription mix, e.g. UC2 (1) UC4 (1)).
UC2 pickup visitsWhat each UC2 partner actually does when it connects: collected, two-way exchange, delivery-only (the UC4 twin) or empty-handed visits.
AccountsThe accounts (partners) and their communication profiles — naming vs configured type/auth, insecure and unrestricted endpoints, conflicting host/whitelist setup, plus account & login integrity checks (non-standard or shared logins, password profiles without a password, and more).
Account sharingWhich accounts serve more than one subscription, and in what shape: UC2+UC4 mailbox pairs, UC1+UC3 outbound pairs, fan-outs and both-directions accounts.
TwinsEvery twin pair on one page: subscriptions that are the same flow configured the opposite way (naming slips highlighted) and the accounts spelled with both separators.
CronjobsThe configured polling schedules (UC3 — ST pulls from the partner), each Quartz cron expression translated to plain English.
Config hygieneThe cleanup backlog: likely-duplicate twins (case / separator folds) and orphaned objects nothing references.
Whitelist auditWhitelisted partner IPs vs the addresses actually connecting: used, connect-only, never seen (prunable), and the sources without any whitelist entry.
Sources and TargetsThe From/To folder paths of every subscription (shown “path @ host” for remote endpoints, like Search): values used as both a source and a target, and sources/targets shared by more than one subscription.
SkippedThe accounts and subscriptions ignored because their name matches the skip list (input/skip.txt) — removed from the config and both logs so no report counts them — plus the skipped transfer/server log-line counts.
Not in Flow ManagerEvery entity value seen in the transfer logs that the current FlowManager configuration does not know — all eight entity lists checked.
Cross ReferencesEvery pair of the eight entities cross-tabulated, both ways — which values appear together on at least one transfer, the configured-but-never-seen pairs flagged.
Cleanup backlogEvery cleanup signal merged into one ranked decommission-candidate list, safest first — config orphans, never-seen subscriptions, unused whitelist addresses, cron-less polls and long-quiet entities.
Partners
Partner scorecardOne composite health score per partner relation, worst first — error share, trend, pickup wait, security posture, endpoint redundancy and silence, every component its own column, with the traffic-concentration panel.
Blast radiusWhat stops when a remote host dies: the Files, subscriptions, applications and partners behind every outbound endpoint, sole-endpoint partners flagged.
Application dependenciesWhich external partners each internal application exchanges Files with — the dependency matrix with traffic weights and dead pairs at 100% Error.
Partner lifecycleThe quiet failure modes of a partner relation: configured but never live, gone quiet after real history, and still transferring on ever fewer flows.
Boxes
Accounts in boxesEvery configured account boxed by what is true of the subscriptions connected to it — the account view of Subscriptions in boxes, joined through the FlowManager configuration rather than by name.
Subscriptions in boxesEvery subscription boxed by what is true of it — its status (OK, Seen, Not seen, Error, Server log only) or any of fifteen problem signals — one column per box, each cell linking into its report or entity view.
TriageThe ranked action list: every subscription that is red, holds staged Files about to expire, or just fell silent — newest flips on the busiest flows first; the per-symptom pages stay the deep-dives.
Errors
Failed SubscriptionsEvery failing subscription with its evidence — the newest failed File of each (drilling into its transfer legs and server log), plus the flows failing in the server log only; view buttons switch to per-leg-count and full-history views.
Error reasonsEvery possible Reason of the Failed Subscriptions pages — how many currently red subscriptions carry it and the newest occurrence; a nonzero row opens the red subscriptions behind it.
Acceptance vs production
Acceptance vs productionThe two environments’ entities compared by name, per type — only in Acceptance, in both (one linked column per environment, with each side’s Files/volume), or only in Production — opening on the Summary.
