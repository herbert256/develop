An account (a partner in the FlowManager config) talks to us through one or more communication profiles, each defining how one endpoint connects. This page checks the accounts, their login names and their profiles for configuration slips. A profile name is coded <TYPE>_<partner>_<AUTH>: the prefix is the connection type — SCP/SSCP = server (ST connects out to the partner), CCP = client (the partner connects in) — and the suffix is the authentication — PWD = password, KEY = public key. Below, both are checked against each profile’s real type and clientAuthentication, followed by the account & login checks.

Breaking naming rules (0)

An incoming account (the partner connects to us) separates its name parts with -; an outgoing one (we connect to the partner) uses _. The same flow configured both ways therefore appears twice, once in each spelling — DPL-AXINI-AO-IMPRESS inbound and DPL_AXINI-AO_IMPRESS outbound. The separator is read the way the partner derivation reads it: _ wins unless splitting on - yields more parts, so an internal hyphen inside one part (AIM-FIN_TREASURY-SP) is not mistaken for the separator.

No breaks — all 35 directional accounts follow the rule.

Not clear domain-application-partner (0)

An account name is meant to read domain / application / partner — ODV_MAIA_AKZO is domain ODV, application MAIA, partner AKZO. These accounts could not be resolved into all three. The check does not re-read the names: it asks the derivation itself what it managed to assign, so a blank column is a value the rest of the site genuinely does not have for that account.

All 36 accounts resolve to a domain, an application and a partner.

FTP endpoints (0) — insecure

FTP transfers credentials and data in clear text and cannot use a public key, so these are the site’s only insecure profiles. They are also exactly the 0 profiles outside the PWD/KEY naming convention above (their name ends in a partner tag and their clientAuthentication is unset). Migrating them to SFTP would close the last plaintext links.
