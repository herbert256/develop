The client polling schedules in subscriptions.json, joined against what actually happens. Where we are the client and pull from the partner (UC3, and UC5’s pull side), ST connects to the partner’s server on a timer and collects whatever is waiting; the schedule is a Quartz cron expression (sec min hour day-of-month month day-of-week), translated to plain English in the Schedule column. (UC1 is a client use case too, but pushes on directory scanning — no cron.) The Observed column says when the schedule actually fires: from the server log’s poll lines where they exist, else from the file arrivals.

Observed slots come from the server log via the Remote poll report — the median of each day’s FIRST poll, ± one standard deviation; a schedule firing more than 3× a day has no single slot and shows its poll rate instead. Slots marked · files fall back to the transfer Punctuality report (same model over file arrivals) for schedules with no poll line. Matching is name-prefix, both ways (the server truncates long site names). A - means no poll and no File in the loaded logs — the schedule never fires. A dark red Observed cell contradicts its schedule: the observed slot sits off the scheduled time, the poll rate is more than 3× off the expected one, or a continuous schedule is only seen firing a few times a day.

Schedules that never complete a poll

The 1 schedule(s) whose Observed column shows -: the server log holds no completed poll for them. Most DO fire — their setup lines appear right on the scheduled minutes (Poll starts) — but the poll dies before the listing. Connection and listing failures name the subscription in the log and are counted directly. Authentication failures name only host + user, so they are matched through the subscription’s configured host and can be shared between that host’s flows. A row with neither starts nor failure lines never fires at all in the loaded logs. The evidence comes from the same server-log pass as the Remote poll report.
