Added BL

What input/<env>/BL.txt contributes on top of the configuration export. A subscription can carry its business-line marker in two places: the tags entries of subscriptions.json (any entry starting with BL), and the hand-maintained file input/<env>/BL.txt, whose rows read <subscription> <BL>[,<BL>...]. The pipeline unions the two, so the BL entity always shows every number a flow has.

This page is the difference: one row per subscription, listing only the BL numbers that come from the FILE and are not among that subscription’s tags. A subscription whose numbers all come from its tags does not appear at all, and an environment whose file adds nothing says so in one line.

The columns

  • Subscription — the configured flow, linking its detail page. Names in BL.txt are matched case-insensitively against the configured subscriptions of that environment, and the configured spelling is what is shown; a row naming a subscription the environment does not configure is skipped by the config step, which reports it on the build.
  • BLs — the added numbers, comma-separated, each linking its own BL detail page (a BL is a full entity, alongside Logical, Partners, Domains and Applications).

Rows are tinted by the subscription’s result — light green = last transfer OK, light orange = configured but never seen, light red = last transfer Error, light blue = surfaced only by the server log.

How it’s computed

The config step (bin/flow-manager.sh) keeps the two BL sources apart while building the union, and writes the file-only rows to xref/_subscriptions-bl-added.tsv. This page renders that sidecar, so it can never disagree with the pipeline that built the BL entity.
