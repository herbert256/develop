File in - File out

What this shows

Partner-to-partner handovers carried by TWO subscriptions. A file arrives from one partner on an inbound subscription, OpsWise copies it across, and the same filename leaves to a different partner on an outbound subscription. Nothing in the transfer data links the two — separate CoreIds, separate accounts, separate partners — except the filename, so without this report each half is counted as an unrelated one-partner flow.

The platform also has a documented single-subscription form of the same idea, the UC5 and UC8 relays (one subscription each today). This report finds the undocumented two-subscription form, which carries far more traffic.

The two tables

Handover routes — one row per (inbound subscription → outbound subscription) pair, busiest first, with the partner on each side and how long the copy takes (fastest / median / slowest).

Latest handovers — the 100 most recent individual files, with the arrival and departure timestamps, the gap, and the size on each side.

How it's computed

One pass over the logical-transfer cache (_files.tsv): every named file with a known movement direction (col 17 in / out) is indexed by filename, and each inbound file is paired with the next outbound file of a different subscription that follows it within 48 hours. Each inbound file pairs at most once.

Matching is on the filename only, deliberately. The largest route re-encrypts in transit (.afp.pgp, growing by 4–19 KB), so requiring the size to match would miss it completely. The size behaviour is reported instead, in the Same size / Size changed columns — an all-same route is a provable byte-for-byte copy, an all-changed route was re-encrypted or re-wrapped.

The 48-hour window is wide because the copy is a scheduled OpsWise batch rather than an event: observed gaps run from 4 minutes to 47 hours. A one-hour window finds roughly a sixth of them.

How much to trust a row

Compare Files with Filenames. When they are equal every match carried a distinct name — and where those names are timestamped, thousands of collisions with one particular subscription cannot be coincidence. A route with far fewer filenames than files is repeating a fixed name (a daily export.zip), which can pair by accident: treat it as a lead, not a fact.

Check the two partner columns as well. When both sides resolve to the same partner group the row is usually not a partner-to-partner handover but a pull-then-stage flow — we fetch a file and stage it back for the same partner. Those rows are kept so the pattern stays visible, but they read differently.

Why the partner grouping does not already show this

The partner derivation merges two partner codes into one organisation when they share a whitelisted IP or an endpoint domain (see Entity coverage). A handover that happens inside OpsWise leaves neither trace, so routes that cross unmerged partners are invisible to it — which is exactly what this report surfaces.
