Account Details

What this shows

This is the per-account detail page — one real page per account name (linked from every Account cell across the site) — not the Accounts list. It opens with a one-line KPI summary, then a set of tables: Activity per day, by weekday and by hour; a breakdown of every other dimension the account's transfers touch (subscription, login, remote host, protocol, AV scan result, security parameters, direction, action-by, mode); and finally the 10 largest transfers seen for this account.

A short Features table near the top lists the account's configured FE Login (the SFTP username partners authenticate as, on inbound flows) and/or its Host endpoint (the address we dial on outbound flows), each linked to that entity's own detail page. It shows on every account page — whether the account has logged traffic or is configured-but-never-seen.

Right after the Latest 100 table sit two connection tables sharing one layout (address · In · Out · Name). Incoming connections unions the account's configured AllowIP whitelist (partners.json, patterns expanded to their addresses) with the source addresses actually observed on the account's incoming connections, colored against the site-wide expanded whitelist. Outgoing connections unions the account's configured endpoints with the hosts observed on its outgoing connections, colored against the configured endpoint list. In / Out count the Files each address moved (In = a file entered us, Out = one left us). Name is the configured endpoint associated with an address by input/<env>/ip/ip-hosts.tsv, and stays blank when the address maps to none; no reverse-DNS lookup is used. On Outgoing connections the IP column holds the endpoint's forward-resolved address(es) and Name the configured hostname. Each row links out: an Incoming row goes to that source address's own page under details/incoming_connections/ (rows for a whitelisted address never actually sighted have no such page and stay unlinked, so only rows with real traffic or a sighting link); an Outgoing row goes to the host's detail page. Row colors: light green = configured and used; light red = traffic from/to an address NOT in the configuration; light orange = configured but never seen — the orange rows load collapsed behind one summary row; light blue = a whitelisted address sighted only in the server log (never a transfer — it stays visible, not folded). Full-period figures — the date filter leaves both tables unchanged.

Two more account-only sections draw on the server log. Files not picked up lists the files File Maintenance eventually purged from this account's folder uncollected (from the log's "Deleted files [ … ]" retention sweeps, keyed on the NAME@FEnnn token) — most-recently-expired first, up to 100, paged 10 at a time. A file here was collected by nobody: a real pickup would have removed it before it could expire. At the very bottom of the page a single Last server log messages table gathers the tail of the server log for this account — its own 25 most-recent lines merged with its configured login(s) and host(s) lines (a host by its configured name and each of its resolved IP addresses, since the server-side caches are address-keyed), plus the 10 most-recent Error/Warning lines of each so a recent problem stays visible even when the newest 25 are all routine. Deduplicated, newest first, full-period (not adjusted by the date filter).

When the server log shows an Error or Warning after this account's last transfer — for the account itself or any entity it is 1-to-1 connected to (typically its one login and one host) — a red banner appears at the top of the page: "ERRORS IN SERVER LOG AFTER LAST TRANSFER – SEE LOG AT BOTTOM OF THIS PAGE", and those connected after-the-fact Error/Warning lines are merged into the table too.

The subscription / login / remote host tables are cross-referenced against the FlowManager configuration: every partner configured for this account is listed, whether it appears in the logs or not. Green rows have logged data; red rows are configured but never seen with it — they carry no counts but do link to that name's own (never-seen) detail page. Partners logged without being configured are listed too (green). Narrowing the date filter re-tints the rows: a partner with no activity in the selected range turns red instead of being hidden.

Last error(s)

Directly above the Features table, a page carries a Last error(s) table whenever any subscription it moves files with has something wrong on it: one row per such subscription — its most recent error, newest first — with the date and time, the subscription and the file. Rows are tinted by kind, red for a failed file and orange for one that expired before the partner collected it, and there is no table at all when nothing connected to this entity has an error.

Clicking anywhere on a row — the subscription name included — opens that file’s error page, with every transfer leg and the server log of the failure. Those are the same files the Failed Subscriptions list holds: that page guarantees every subscription’s last error has a page, which is what lets this table link straight to it.

Direction, page colors and never-seen pages

Every configured name from the FlowManager exports has a page — seen in the logs or not — and the page background color says the same at a glance: light brown = seen & in, light blue = seen & out, light gray = seen & both/unknown, light yellow = never seen & in, light orange = never seen & out, light purple = never seen & both/unknown. A never-seen page opens with a "configured, never seen" line and shows the configured cross-references (all red) and any whitelisted IPs.

An entity configured both ways splits every outcome into four columns — In - Error / In - OK / Out - Error / Out - OK — by each file's own direction; a file with no direction of its own counts in Files and Volume only.

When a page carries both green (logged) and red (configured-only) rows, the tint tells them apart at a glance. The Activity per day table leads with the Files count; the Subscription breakdown comes first below it, and the Account breakdown renders right under the Incoming/Outgoing connections tables.

How it's computed

The KPI line reports this account's rank and share of traffic among all accounts, its failure rate, total volume, and cadence (days active, median gap between active days, days idle since last seen). Where a duration is recorded, it adds processed-transfer performance (average/p50/p95/max duration and throughput) and a distinct session count. Every count on the page is in Files: one per logical transfer, split by its delivered (final-row) outcome, with volume counted once per file.

A Partner, Application, Domain or Logical breakdown holding exactly one row is folded away: the name appears as a row in the Features table instead, keeping its link and colour.
