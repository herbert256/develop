Transfer Patterns

What this shows

A logical transfer (one File) is built from an Inbound row, an Outbound row, and — when the Outbound fails — up to 5 Outbound retries (the Inbound can retry too). This report groups Files by their pattern: the ordered sequence of "Direction / Status" lines across all of a File's rows, e.g. an Inbound row that processed followed by an Outbound row that processed. Status is shown exactly as logged, so a value like "Failed Subtransmission" appears verbatim rather than folded into the Error bucket.

Each distinct pattern is one row of the table. The Last 10 files column lists the 10 Files that most recently matched the pattern ("date time  CoreId"), newest first. The Pattern and Last 10 files cells load collapsed: only their first and last line show, with an ellipsis (⋯) marking the hidden middle lines — so a collapsed pattern shows its first and last leg. Click a cell to expand it; click again to collapse.

How it's computed

Rows sharing a File are ordered Inbound-first, then by start time (so retries appear in the order they happened), and their "Direction / Status" lines are joined into one pattern string. The Legs column counts the lines in the pattern — the physical rows a matching File is made of. The Files column counts how many logical transfers matched that exact pattern. The Transfers column counts their individual physical rows — Files × Legs — so a two-leg pattern (Inbound + Outbound, no retries) contributes twice as many Transfers as Files.

There are typically only a few dozen distinct patterns; the table is capped at the top 200 by frequency as a safety margin, and a note appears if any were cut off.
