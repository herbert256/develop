Could not send file

What this shows

Every Could not send file error the server log holds, one row per line, newest first: an Advanced Routing route that gave up delivering a file to its transfer site after its retries. The line looks like this:

AR0074: [SECURETRANSPORT] [UC1_CD_IDM_ROTAFORM] Could not send file: {/.stfs/objects/…/krpdashboard-productie-20260910135425809.xml} using transfer site: {UC1_CD_IDM_ROTAFORM_SFTP_SERVER_ROTAFORM} after attempting {11} times.

The table

  • Date & time — when the route gave up, to the second.
  • Subscription — the route, the second bracket of the line; it opens the subscription's detail page, and the row carries the subscription's result colour.
  • File — the last element of the path in the first braces.

How it's computed

The tokenized server log is scanned for TM lines whose message starts with an AR<n>: code and carries “Could not send file:”. The subscription is read from the second bracket group (the same reading the UC1 status report and the failure pages' “Duplicate file” reason use), folded to its current name when it was renamed; the file is the basename inside the first braces. The report shows at most 1000 rows and at most 10 rows per subscription — the newest ones on both counts; the intro and the total row say how many lines the log really holds. The date filter, search and sort work over the shown rows.

Why it matters

This error is the delivery leg failing for good: the platform tried the configured number of times and the file did not reach the transfer site. Each row is a file a partner did not get; a subscription that keeps appearing has a delivery-side problem — the transfer site, its credentials or the far end — that the Errors reasons and the subscription's own detail page put in context.
