Remote Host Details

What this shows

The per-remote-host detail page — one real page per host (linked from every Remote Host cell across the site). It opens with a KPI line, then Activity per day/week/hour/weekday, a breakdown of every other dimension this host's transfers touch (account, subscription, login, protocol, AV scan, security parameters, direction, action-by, mode), and the 10 largest transfers seen for it.

Right after the Latest 100 table sit two connection tables sharing one layout (address · In · Out · Name). Incoming connections unions the allowed source addresses of the partner this host is configured under (its AllowIP whitelist, patterns expanded) with the addresses actually observed on incoming connections attributed to this host. Outgoing connections lists the host itself as a configured endpoint plus any hosts observed on its outgoing connections. In / Out count the Files each address moved (In = a file entered us, Out = one left us). Name is the configured endpoint associated with an address by input/<env>/ip/ip-hosts.tsv, and stays blank when the address maps to no configured endpoint; no reverse-DNS lookup is used. On Outgoing connections the IP column holds the endpoint's forward-resolved address(es) and Name the configured hostname. Row colors: light green = configured and used; light red = traffic from/to an address NOT in the configuration; light orange = configured but never seen — the orange rows load collapsed behind one summary row; light blue = a whitelisted address sighted only in the server log (never a transfer — it stays visible, not folded). Full-period figures — the date filter leaves both tables unchanged.

The account / subscription / login tables are cross-referenced against the FlowManager configuration: every partner configured for this remote host is listed, whether it appears in the logs or not. Green rows have logged data; red rows are configured but never seen with it — they carry no counts but do link to that name's own (never-seen) detail page. Partners logged without being configured are listed too (green). Narrowing the date filter re-tints the rows: a partner with no activity in the selected range turns red instead of being hidden.

At the very bottom a Last server log messages table shows the tail of the server log for this host: its 25 most-recent lines merged with its 10 most-recent Error/Warning lines, plus the Error/Warning messages of its 1-to-1 connected entities (its one account, subscription, login) that occurred after the host's last transfer. If any such after-the-last-transfer Error/Warning exists, a red banner appears at the top: "ERRORS IN SERVER LOG AFTER LAST TRANSFER – SEE LOG AT BOTTOM OF THIS PAGE". Deduplicated, newest first, full-period.

Last error(s)

Directly above the Features table, a page carries a Last error(s) table whenever any subscription it moves files with has something wrong on it: one row per such subscription — its most recent error, newest first — with the date and time, the subscription and the file. Rows are tinted by kind, red for a failed file and orange for one that expired before the partner collected it, and there is no table at all when nothing connected to this entity has an error.

Clicking anywhere on a row — the subscription name included — opens that file’s error page, with every transfer leg and the server log of the failure. Those are the same files the Failed Subscriptions list holds: that page guarantees every subscription’s last error has a page, which is what lets this table link straight to it.

Direction, page colors and never-seen pages

Every configured name from the FlowManager exports has a page — seen in the logs or not — and the page background color says the same at a glance: light brown = seen & in, light blue = seen & out, light gray = seen & both/unknown, light yellow = never seen & in, light orange = never seen & out, light purple = never seen & both/unknown. A never-seen page opens with a "configured, never seen" line and shows the configured cross-references (all red) and any whitelisted IPs.

An entity configured both ways splits every outcome into four columns — In - Error / In - OK / Out - Error / Out - OK — by each file's own direction; a file with no direction of its own counts in Files and Volume only.

When a page carries both green (logged) and red (configured-only) rows, the tint tells them apart at a glance. The Activity per day table leads with the Files count; the Subscription breakdown comes first below it, and the Account breakdown renders right under the Incoming/Outgoing connections tables.

How it's computed

The KPI line adds this host's rank and share among all remote hosts, failure rate, volume, cadence, and processed-transfer performance where a duration is recorded. When the page is for a configured endpoint hostname rather than a raw IP, the KPI line also lists the address(es) associated with it in the forward-resolution map — one configured hostname can have several addresses over time. Every count on the page is in Files, counted as distinct (host, CoreId) pairs — a File touching several hosts counts once on each host's page.

A Partner, Application, Domain or Logical breakdown holding exactly one row is folded away: the name appears as a row in the Features table instead, keeping its link and colour.

The Logons table

The page carries a Logons table like the login pages’, telling both directions of the server-log connection story. Inbound — when this host’s addresses connect to us: the first successful authentication, the pattern, the count (newest in the Last column), plus the Allowed and Disallowed whitelist-screening counts, the only funnel families whose lines carry the client address. Outbound — when we connect to it: Connections (out) counts every connection SecureTransport opened toward its addresses, with its own first stamp and pattern, the red rows classify our failed connection attempts at it — Timeouts (socket timeouts, PeSIT “317 Time out” aborts), SSH errors (the SSH layer failing without further detail), Network errors (network incidents, refusals, drops), TLS handshake (bad/unknown certificate, handshake failure), Too many connections, SSH negotiation (algorithm mismatch, rejected host key) and Proxy errors (SOCKS) — and Auth failures (red) counts our authentication failures at it — the same evidence as the Logon report’s Outgoing tab, split beneath it into that tab’s categories: Password, Key, Certificate and Other, each with its own last occurrence. The Features, Activity per day and Logons tables sit side by side at the top of the page. An endpoint’s figures sum over its resolved addresses; a host with no connection evidence in either direction has no such table.
