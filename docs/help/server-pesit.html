PeSIT

What this shows

Per-day activity from the PESITD component — the platform's PeSIT protocol layer: client logins and logouts, inbound transfer completions, network resets, and hits against the "exceeded the maximum number of allowed connections" ceiling (the connection limit is 100). All PeSIT traffic on this platform is the internal cluster CFT (caller P14303_CFT01, remote hosts 145.219.156.20/.21), so there is no partner dimension worth breaking out — this is a per-day capacity and stability view of one internal link, not a partner-facing report.

How it's computed

One row per calendar day, with calendar gaps filled in as zero rows so a quiet day is visible rather than missing. Logins/Logouts come from "Client logged in/out" messages; Transfers from "Inbound transfer completed with diagCode"; Conn resets from PESITD "Network error: Connection reset" messages (the same events also feed into the Transfer Error Reasons report); Max-conn hits from "PeSIT server has exceeded the maximum number of allowed connections 100" — the internal CFT link saturating its connection limit.

Conn resets are tinted red, Max-conn hits amber. All counts are additive and re-total under the date filter. Click a day to expand its 10 most recent Warning/Error lines (newest first).

The problem tables

The page also carries the PeSIT problem view (absorbed from the former PeSIT Problems report, 2026-07): every problem line the ST ↔ CFT link produces, in three tables. Problems per day splits the lines into the outbound (ST → CFT, the TM component — ST as PeSIT client) and inbound (CFT → ST, the PESITD component — ST as server) legs. Problem types classifies each line by message shape: Transfer rejected/refused is the CFT saying no; Checkpoint mismatch a restart disagreement; Connection reset / network incident the link dropping; the connection-limit classes are the capacity ceilings on either side. PeSIT diagnostic codes lists the protocol's own diagCode taxonomy (2xx transfer-level, 3xx connection-level). Counts are log lines, not failed transfers — one failure commonly logs several lines — and the protocol lines carry no flow names, so this stays a link-health view with no per-partner attribution.

The Outbound FPDU ledger counts the TM PeSIT client’s Info-level protocol confirmations per FPDU kind and diagCode — refusals and aborts that never surface in the error reports, such as connections refused with “Too many connections”.

About this report

How busy the platform is and what it cleans up: PeSIT activity — logins, transfers, resets, ceiling hits and diagnostic codes — and the file retention / cleanup sweeps per account and remote directory. (The session-concurrency view went with the session bookkeeping lines the server parse now drops — 2026-08.)

One row = one calendar day. Logins/Logouts come from "Client logged in/out"; Transfers from "Inbound transfer completed with diagCode"; Conn resets from PESITD "Network error: Connection reset" (also counted in Transfer Error Reasons); Max-conn hits from "PeSIT server has exceeded the maximum number of allowed connections 100" — the internal CFT link saturating the 100-connection limit. Counts are additive, so a date-filtered range re-totals them. Conn resets are tinted red, Max-conn hits amber. Click a day to expand its 10 most recent Warning/Error lines (newest first).

ST → CFT counts the TM component acting as PeSIT client (SecureTransport dialing the CFT); CFT → ST counts the PESITD component acting as server (the CFT dialing SecureTransport). One failed transfer commonly logs SEVERAL lines — the client-side wrapper plus FPDU_AWRITE/FPDU_ABORT pairs — so these are log lines, not failed transfers. Click a day for its 10 most recent problem lines (newest first).

The problem lines classified by their message shape, most frequent first. Transfer rejected/refused classes are the CFT saying no (negative FPDU_ACREATE / SEND_CONF) — file-side or configuration issues on the CFT; Checkpoint mismatch is a restart disagreement after an interrupted transfer; Connection reset and network incident are the link itself dropping; the two connection limit classes are capacity ceilings, one per side (ST refuses above 100 inbound connections, the CFT refuses with RCONNECT 309 outbound). Click a row for that problem's 10 most recent lines. First/Last seen stay full-period under a narrowed date range.

The PeSIT protocol's own error taxonomy (the diagCode=N the messages carry; lines without a code — connection resets, ceilings — are not in this table). 2xx codes are transfer-level (213 refused/file error, 214 checkpoint), 3xx are connection-level (309 too many connections, 399 generic/SSL). The Share is of ALL problem lines at the full range, so the codes need not sum to 100% (a narrowed date range re-shares over this table only).

Every PeSIT protocol confirmation the TM component logs while acting as PeSIT CLIENT (ST → CFT), per FPDU kind and diagCode — connectionConfirmation (session setup), sendFileConfirmation (per file sent) and abortIndication (transfer torn down). These are Info-level lines, so a refusal here is INVISIBLE to the error reports: diagCode 309 is the CFT refusing the session ("Too many connections"), 310 a network-incident abort, 214 a checkpoint mismatch on restart, 0 success. The Problem types table above counts the E-level wrappers of the SAME failures — this ledger counts only Info lines, so the two never double-count. Click a row for its 10 most recent lines.

AR0089 "Deleting local file: {…}" — the staged local copy removed after a leg completes, attributed to the account (endpoint stripped). Shown as logged; an account known from the transfer logs links to its detail page. Additive; re-totals under the date filter.

"Deleting remote file: <file> under <dir>." — files removed from a partner folder after they were picked up, grouped by the remote directory.

"Start File Maintenance …" vs "File Maintenance … finished." A finish is only logged when the sweep actually deleted files, so far fewer finishes than starts is normal (most runs find nothing to remove). A big gap for one account, or none finishing, is worth a look.
