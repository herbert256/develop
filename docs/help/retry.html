Repeat Failures

What this shows

Transfer "flows" — each distinct (Account, Subscription) pair — ranked by how persistently they fail: flows that have never succeeded are listed first, then the flakiest by failure count. For each flow it shows how many distinct days it failed on, its failure and success counts, how many of its rows were flagged as resubmissions, and the time of its last failure.

How it's computed

The Account+Site pair is used as the stable flow key because file names carry timestamps (so an exact retry never repeats as a name), but the pair that keeps failing is the same account talking to the same subscription over and over. This report counts physical rows from the parse cache (every row is either a failure or a success), not Files — a chronically-broken flow's individual failed attempts are what's being measured here, not distinct logical transfers.

A row's Resubmitted flag comes straight from the log's own resubmission marker (set when an operator resubmitted the transfer by hand — the platform's own automatic retries never set it; the Top view's Recovered columns split the healed Files by it into Automatic and Manual). "Fail days" counts the distinct calendar days a flow logged at least one failure — a flow that fails once a day for a week looks very different from one that failed 50 times in a single afternoon, even with the same total failure count. Only flows with at least one failure are listed; a flow that always succeeds never appears.

Resubmission outcomes (server log) compares the server’s own per-day resubmit errors and successes — it also catches attempts that never produced a transfer-log leg.
