Retries & resubmissions

What it shows

  • Transfers that did not succeed at the first attempt: the failing flows, the retries inside a File, and the manual resubmissions.

Tabs

  • Failing flows — the top 60 Account + Subscription pairs, never-succeeded first: Fail days, Error / OK transfers (legs), Resubmitted legs, Last failure.
  • Legs before success — OK Files (Waiting included) by failed legs before success: Attempts, Files, % of OK Files.
  • Gave up — the same for Files ended Failed or Expired; its 0-failed-legs row is mostly Expired.
  • Retry spacing — a failed leg’s start to the File’s next leg: Gap, Retries, Files.
  • Failing side — Failed legs and Files per Direction: inbound = arrival at ST, outbound = delivery onward or partner pickup.
  • Resubmitted per day — Resubmitted legs, their own Error / OK status, Files.
  • Per subscription — Resubmitted legs, Files, First, Last.
  • Resubmission outcomes — the server log’s resubmit outcomes per day, Error and OK, including attempts that left no transfer-log leg.
  • Recovered files — its own help.

Rules

  • Failing flows counts legs, not Files: a failed leg re-sent OK counts on both sides.
  • Resubmitted = the transfer log’s own flag, set only by a manual resubmission, never by an automatic retry.
  • Under a narrowed date range the Files columns and First / Last stay full-period.

Tips

  • Under 10 seconds between attempts = automatic hammering; minutes or hours = scheduled re-runs.
  • A count cell drills to its 10 most recent transfers or Files.
