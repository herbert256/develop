Logical detection

What this shows

One row per configured FlowID (the customAttribute_FlowIdentifier value of the subscriptions): the Logical flow group it detected to, and the rule trail the derivation applied to get there — in firing order, ;-separated. The Logical cell links its detail page, and rows tint by the Logical’s result.

The rules

  • separators normalized — before any splitting, - folds to _, doubled separators collapse and edge separators trim.
  • 4 parts: … dropped / shared / numeric — the variant-fold family: a 4-part FlowID joins its bare 3-part name, a shared 3rd part, a shared first-3 prefix, or drops a purely numeric part.
  • digit tail stripped — numbered variants (…2) fold onto the stripped form when it exists or 2+ share it.
  • 5+ parts: longest existing prefix — a long FlowID joins the longest 3+-part prefix that is itself a FlowID.
  • pinned in input/logical.txt — a fixed mapping took the Logical verbatim (also shown when the pin caught the folded spelling, or the group name a fold landed on).
  • 2/4/5 parts: … combined — the 3-part reshape: parts joined with - (the hyphen marks combined parts, which is why Logical names are never separator-folded), guided by the known 2nd/3rd-part vocabulary.
  • forced: … — nothing else fit: the first part stays, a known 2nd/3rd part anchors, the rest combines.
  • 3 parts — kept as-is — the FlowID needed no work.

How it’s computed

The trail is written by the derivation itself (bin/flow-manager.sh → xref/_logical-rules.tsv) as it derives the FlowID → Logical map, so this page and the pipeline can never disagree.
