Logical detection

What it shows

One row per configured FlowID (the subscriptions’ customAttribute_FlowIdentifier): the Logical flow group it detected to and the rule trail the derivation applied, in firing order, ;-separated. The Logical cell links its detail page; rows tint by the Logical’s result.

Rules (as named in the trail)

  • separators normalized — before any split: - folds to _, doubled separators collapse, edge separators trim.
  • numeric-only parts removed — a name of more than three parts drops every purely numeric part (AB_EUROPORT_EQUENS-1 → AB_EUROPORT_EQUENS): a number is a sequence tail, never a domain, application or partner. Three parts or fewer keep theirs.
  • 4 parts: … dropped / shared — the variant fold: a 4-part FlowID joins its bare 3-part name, a shared 3rd part or a shared first-3 prefix. Exception: a 4th part that is a known 3rd part of a 3-part FlowID drops nothing — the reshape keeps the first and last parts and combines the 2nd and 3rd.
  • digit tail stripped — numbered variants (…2) fold onto the stripped form when it exists or 2+ share it.
  • 5+ parts: longest existing prefix — joins the longest 3+-part prefix that is itself a FlowID.
  • pinned in input/logical.txt — a fixed mapping took the Logical verbatim (also when the pin caught the folded spelling, or the group a fold landed on).
  • 2 parts: UNKNOWN inserted as the application — two parts name a domain and a partner; UNKNOWN takes the middle (WA_VDN → WA_UNKNOWN_VDN).
  • 4/5 parts: … combined — the 3-part reshape: parts joined with - (the hyphen marks combined parts, which is why Logical names are never separator-folded), guided by the known 2nd/3rd-part vocabulary.
  • forced: … — nothing else fit: the first part stays, a known 2nd/3rd part anchors, the rest combines.
  • 3 parts — kept as-is — no work needed.

Source

  • The trail is written by the derivation itself (bin/flow-manager.sh → xref/_logical-rules.tsv) while it derives the FlowID → Logical map, so this page and the pipeline can never disagree.
