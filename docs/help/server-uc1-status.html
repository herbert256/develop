UC1 status

What this shows

Every configured UC1 subscription — the push use case, where we are the client and send a file out to the partner as soon as one appears — in exactly one of six statuses. It is one of a set of four: UC2 status does the same for the flows the partner collects from us, UC3 status for the ones we poll and pull, and UC4 status for the ones the partner delivers to us. The info boxes above the table give the count per status. One row per subscription:

  • Status — one of six, a complete partition (see below).
  • Subscription — the configured name, linking to its detail page.
  • Files / OK / Error / Last file — the transfer-log history: logical transfers pushed out, split by outcome, and the date of the newest one. All blank on a subscription the transfer log has never seen.
  • Route runs — how often Advanced Routing started this subscription's route. A UC1 push is one route run per file, so this is roughly "how often did we have something to send".
  • Problems — server-log lines saying the send could not be made, or that the partner could not be reached at all.
  • Last log — the newest server-log line of either kind. It answers "is this flow still running at all", so on a server - error row it can be newer than the failures the drill shows: the route still runs, it just last failed earlier.

The six statuses

The first three are the transfer-log verdict, read off the subscription's site-wide result colour:

  • ok (green) — its latest File was delivered. The flow is working.
  • error (red) — its latest File failed and it has never once delivered an OK File in the window. Nothing here ever worked, which points at the configuration or a partner side that was never finished rather than at something that broke.
  • ok -> error (red, was green) — its latest File failed, but it has delivered OK Files before: a regression. Something that used to work stopped, so there is a change to find.

Then the blue subscriptions — seen in the server log, never once in the transfer log. They have no transfer history at all, so the log's own lines are the only evidence there is:

  • server - error — a failure names the subscription: Could not send file, An error occurred while sending, a routing step that finished with error, or a Connection failure reaching the partner in the first place.
  • server - no result — the server log has seen the subscription, but no failure names it. It can still have been marked blue on a line attributed to its host or account rather than to itself — in one real estate the single case was a failed test connection to the partner host — and its detail page shows that line.

And last, the largest:

  • not seen (orange) — configured, and never observed in either log. Not a failure so much as an open question: a flow that was set up and never used, or one whose partner side was never finished. In one real estate this was 97 of 185 subscriptions, more than half the report.

How it's computed

The roster is every UC1 name in the FlowManager subscription export, so a subscription appears whether or not it has ever run. Green/red/blue/orange is the site-wide result colour; Files/OK/Error come from the transfer cache (_files.tsv), and the route signals from the server parse cache.

error vs ok -> error is a per-File question, not a per-day one: right after any OK File the subscription was green, so a red subscription with even one OK File in the window counts as a regression. That is deliberately finer than From green to red, which buckets by whole days and so misses a flow that fails at the end of every day while still delivering within them.

The server counts come from the Advanced Routing (AR…) lines, which carry the route name in their second bracket group (ARn: [account] [route] …), plus the two client-side failures that mean we never reached the partner at all.

How it differs from UC3 status

Two deliberate differences, both because a push is not a pull:

  • There is no "no files" status. UC3 polls, so "the poll worked and there was nothing to fetch" is a real and common state with its own log line. A UC1 push is triggered by a file appearing, so no file simply means no route run and no log line — there is nothing to report.
  • "not seen" is a first-class status here, not the safety net it is on UC3 status. More than half the UC1 subscriptions are in it; UC3 has none at all, so its box stays hidden there.

The blue split also needs no tie-breaker. On UC3 two rival explanations — empty polls and failures — compete on the same subscription, so the most recent line arbitrates. Here only one explanation is on offer, so a blue subscription either has a failure or it does not.

Why it matters

A UC1 flow is the one where we are the active party, so a failure is ours to fix: our route ran, our send failed, our connection was refused. That makes the red and server - error rows directly actionable in a way an inbound flow's are not. The large not seen block is a different question and worth a periodic look — configuration that has never carried a file is either waiting on a partner or should not be there, and either way it is quietly counted as part of the estate.

Every UC2 (collect-from-us) flow, classified. Never collected (red): File Maintenance deleted staged files and nothing was ever collected — logon visits alone do not count. No files (amber): the partner DOES log in to collect (pickups > 0) but the app never staged a single file — a dormant or broken source side. Both (green): the partner provably collects (Files in the transfer log) AND the odd file still expired — both outcomes on the one flow. OK (green): files collected, none expired — healthy. Nothing (plain): no collection and no expiry — a quiet flow, one whose partner collects over CFT (which logs no SSH pickup), or one whose visits have so far come up empty. Uncollected detection stays on the retention delete on purpose — arrival + no-pickup would flag almost every pickup flow, since CFT-collecting partners never log an SSH pickup; No files and OK need the SSH signal, so they only distinguish SFTP-collecting partners (a CFT partner with no expiry lands in Nothing). A logon whose session only delivered files (the account's UC4 twin flow handing files over) is not a pickup and is not counted. Arrived dates come from the transfer log. One row per flow: an account serving several UC2 flows (the hybrid production accounts) lists each with its own staged, collected and expired Files, while the Pickups figures are the account's — the partner logs on to the account, not to a flow. On an account carrying several FE logins, the Pickups figures are the flow's own login's instead: each login is a different partner credential, so its logons prove nothing about the other logins' flows. The client polling schedules in subscriptions.json, joined against what actually happens. Where we are the client and pull from the partner (UC3, and the pull side of UC5), SecureTransport connects to the server of the partner on a timer and collects whatever is waiting; the schedule is a Quartz cron expression (sec min hour day-of-month month day-of-week — reference below), translated to plain English in the Schedule column. UC1 is a client use case too, but pushes on directory scanning — no cron. All schedules are enabled; none skip holidays. Rows are tinted by the result of the subscription — green OK, orange never seen, red Error, blue seen only in the server log.

Observed says when the schedule actually fires — from the poll lines of the server log where they exist (the Polls by subscription table above: the median of the FIRST poll of each day (the first and the last active day left out — the export window cuts into both), ± one standard deviation; a schedule firing more than 3× a day has no single slot and shows its poll rate instead), else from the file arrivals: slots marked · files fall back to the transfer Punctuality report (the same model over file arrivals). Matching is name-prefix, both ways (the server truncates long site names). A - means no poll and no File in the loaded logs — the schedule never fires. A dark red Observed cell contradicts its schedule: the observed slot sits off the scheduled time, the poll rate is more than 3× off the expected one, or a continuous schedule is only seen firing a few times a day.

The 5 schedule(s) whose Observed column shows -: the server log holds no completed poll for them. Most DO fire — their setup lines appear right on the scheduled minutes (Poll starts) — but the poll dies before the listing. What goes wrong is the dominant failure line the server log pairs with the flow; Failure lines counts them all.

Connection and listing failures name the subscription in the log and are counted directly. Authentication failures name only host + user, so they are matched through the configured host of the subscription and can be shared between the flows of that host. A row with neither starts nor failure lines never fires at all in the loaded logs. The evidence comes from the same server-log pass as the Polls by subscription table above.

The server counts are account-keyed, because a partner connects to an account and the subscription name barely reaches the log — the join is 1:1 for UC4. Logons counts the "successfully authenticated" server-log line — one per successful SSH logon (an "Allowed user" whitelist admission that then fails authentication does not count). Arrivals is a file actually handed over ("will be submitted for processing"), Problems a logon the account whitelist refused. Because we are the SERVER here, there is no unreachable-partner failure to have: the only way a UC4 flow breaks before a file exists is the partner being turned away, which is exactly server - error.
