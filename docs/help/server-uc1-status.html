UC1 status

What it shows

Every configured UC1 subscription (the push use case: we are the client and send a file out as soon as one appears), one row each, in exactly one of six statuses; the info boxes count them. Siblings: UC2 (the partner collects from us), UC3 (we poll and pull), UC4 (the partner delivers to us).

Columns

  • Status — one of six, a complete partition (below).
  • Subscription — the configured name, linked to its detail page.
  • Files / OK / Error / Last file — Files pushed out, by outcome, and the newest one’s date (_files.tsv); blank on a never-seen subscription.
  • Route runs — “Starting execution of route” lines; one run per file, so roughly “how often did we have something to send”.
  • Problems — a send that could not be made (“Could not send file”, “An error occurred while sending”, a step “finished with error”) or the partner unreachable (a Connection failure, a failing directory listing).
  • Last log — the newest line of either kind: “is this flow still running at all”. On a server - error row it can be newer than the failures shown — the route still runs, it last failed earlier.

Statuses

  • ok (green) — its latest File was delivered.
  • error (red) — its latest File failed and no OK File in the window: nothing ever worked — the configuration, or a partner side never finished.
  • ok -> error (red, was green) — OK Files before, the latest failed: a regression, a change to find.
  • server - error (blue) — never in the transfer log; a Problems-type failure names the subscription.
  • server - no result (blue) — seen in the server log, no failure names it; it may be blue on a line attributed to its host or account (a failed test connection, say) — its detail page shows that line.
  • not seen (orange) — configured, in neither log: set up and never used, or a partner side never finished. Not a failure, an open question — usually the largest block, worth a periodic review.

Rules

  • Roster: every UC1 name in the FlowManager subscription export, run or not. Colour = the site-wide result: green/red are real transfer data (the LAST File OK / Failed-or-Expired), blue server log only, orange neither log.
  • error vs ok -> error is per File — right after any OK File the subscription WAS green — finer than From green to red, which buckets by whole days.
  • Server counts read the Advanced Routing lines of the server parse cache (ARn: [account] [route] …, the route in the second bracket) plus the two client-side failures that mean we never reached the partner.
  • No “no files” status, unlike UC3: a push is triggered by a file appearing — no file, no route run, no log line. The blue split needs no tie-breaker: a failure is the only explanation on offer.
  • We are the active party, so red and server - error rows are ours to fix (our route, our send, our connection).

Tips

  • Click a row for its most recent server-log lines; on a server - error row those are the failures.
