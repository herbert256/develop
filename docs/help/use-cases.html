Use cases

What this shows

The configured subscriptions grouped by their UC<n> name prefix, on two tabs sharing one page group (a third tab, Use Case patterns, groups the accounts by their subscription mix). Both tabs list every use case with a published FlowManager template (the templates.json export) — including one that no subscription uses yet, which shows blank counts on the operational tab.

The Use Case traffic tab is the operational view, with the same status columns as the Flow manager Entities table: per use case the Total configured subscriptions, Seen (= Transfer + Server), Transfer (seen in the transfer logs), Server (surfaced only by the Server → Transfer step: they appear in the server logs but never in the transfer logs), and the result split Error / Warning / Ok — the subscription's most recent transfer ended Error / OK, a never-seen subscription counting as Warning (Total = Server + Error + Warning + Ok). Every nonzero count links a detail page listing exactly the subscriptions it counts, each linked onward to its own subscription page. The Description column carries each UC's one-line meaning for context.

The Use Case definitions tab explains what each UC prefix means: Trigger — what starts the flow (OpsWise = our automation initiates: UC1, UC8; Partner = the partner connects in: UC2, UC4, UC7; Cronjob = a Quartz receive scheduler polls the partner: UC3, and the pull side of UC5/UC6); From / To — where the file travels, Internal (our own systems, over the internal CFT hub) or External (a partner); We are — whether SecureTransport acts as client or server on the connection; and We — whether we send, receive or relay. UC1–UC4 bridge one partner to our internal application; UC5–UC8 are direct relays with no CFT leg, one per source/target push-pull combination: UC5 we pull → we push (two external partners), UC6 we pull → the target collects, UC7 the source delivers → the target collects, UC8 the source delivers → we push (in practice two internal systems). UC6 and UC7 have a published template but no subscriptions yet, so their rows are template-derived. Below the table, a consistency check verifies that every subscription's configured direction agrees with its UC prefix (UC1/UC3/UC5 outbound, UC2/UC4/UC7 inbound; the mixed relays UC6/UC8 are exempt) and flags any exceptions.

The definitions tab ends with a Templates table — the published FlowManager flow templates the use cases are built from. Route is the template's flow pattern: the transport chain a subscription instantiates (source leg → SecureTransport/CFT → target leg). Subscriptions counts the configured subscriptions created from each template, matched on the subscription's pattern; the table total reconciles with the operational tab's Total. UC1 and UC3 each exist in two template variants — relayed through SecureTransport (ST) or handled by the internal CFT hub directly (CFT) — so their per-template counts split what the operational tab shows as one row. The 🔗 icon opens the template in FlowManager.

How it's computed

Subscriptions come from the FlowManager configuration export (subscriptions.json, via data/<env>/flow-manager/base/_subscriptions.tsv); each contributes the leading UC<n> token of its name. The status buckets read that base cache's result column, filled by the build's Server → Transfer and result steps. The definition rows come from one shared table (bin/uc-cases.sh) that also feeds the Subscription detail pages' Summary, so the two never disagree. The template catalog comes from the templates.json export via data/<env>/flow-manager/xref/_templates.tsv; a template's flow pattern equals the pattern recorded on its subscriptions, which is how the per-template counts are joined. Without that export the pages fall back to the subscription-derived UC list and the Templates table is omitted.
