Failure Episodes

What this shows

The other failure reports show failure rates; this one shows failure runs in time. Per subscription, consecutive failed Files are collapsed into episodes — an unbroken run of failures ended by the next OK File (or still open). Three tables:

  • Open incidents — the headline: subscriptions whose latest File failed, with 3+ consecutive failures behind it. Broken right now, not historically: how many failures deep, failing since when, days failing, and the last OK ever — "never" means the flow has never delivered a single OK File.
  • Episodes per subscription — every subscription that failed at least once: episode count, longest run, and how its closed episodes healed (within an hour / within a day / longer). Many quick-healing episodes = a flapping flow; few long ones = a flow that breaks hard.
  • Time to recovery — the distribution over all closed episodes, from an episode's first failure to the next OK.

How it's computed

Logical transfers (Files, the delivered outcome) are walked chronologically per subscription. A failure after an OK (or at the start) opens an episode; the next OK closes it and its recovery time is the gap between the episode's first failure and that OK. A run that reaches the end of the data window with no OK is an open incident; "days failing" counts to the dataset's last day, not today. Click a row for its 10 most recent failed Files.

Why the date filter is off

An episode is a sequence in time — narrowing the date range would cut runs in half and turn open incidents into closed ones. The page therefore always shows the full period (like Stale Accounts).

How it relates to the other failure reports

Failure rate answers "what share fails", Repeat failures counts the physical retries inside one transfer, Anomalies flags unusual hours; this page answers "what is broken right now, how deep, and how long do outages last".
