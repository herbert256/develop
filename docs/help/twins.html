Twins

What it shows

Every Twin relation the detail pages know, collated; each pair once (the relation is symmetric, the detail pages carry it on both sides). Configuration only, no log data.

Rules

  • Subscription twin = the same flow configured the opposite way: the UC2+UC4 mailbox pair (partner drops and picks up over one connection) or the UC1+UC3 outbound pair (we push to and poll the same partner).
  • Detection rules, unioned (one pair can be proven several ways):
    • name — same name body, opposite side.
    • shared login — one FE login (the partner’s actual credential) serves both the UC2 and the UC4 flow, even across accounts; the login-less UC1+UC3 mirror pairs an account whose only two subscriptions are that UC1 and that UC3.
    • spelling-twin accounts — each side’s account is the other spelled with the other separator.
  • Naming slip = proven only by login or account: the flows belong together but their names disagree — the rename backlog.
  • Account twin = one partner relation configured under both separator spellings (- vs _), as tracked by the Separator collision analysis and Config hygiene; renaming one side merges the pair.
  • A formatter over the pair maps the detail-page build persists, so this page and the detail pages’ Twin rows never disagree.

Columns

  • Detected by — which rule(s) proved the pair.
  • Login — the FE… service login the pair connects with (FlowManager configuration); a mailbox pair usually shares ONE login (the twin relation from the credential side), linked to its detail page.
  • Different logins list both; an out-only UC1+UC3 pair shows -: outbound flows hold the remote credential in the communication profile, not a login.

Tips

  • Opens naming slips first; every header sorts; the detection and use-case boxes above narrow the rows.
