Logon

What it shows

The SSH authentication story. Incoming: one row per configured login (the SSH username), columns following the screening funnel, plus door knockers and successful logons. Outgoing: this server failing to authenticate at partners.

Incoming columns

  • Allowed — source address passed the account’s AllowIP whitelist.
  • Authenticated — credentials passed too; logged for every account, whitelisted or not, so it can exceed Allowed.
  • Disallowed — address rejected by the whitelist: the partner (or someone with its credentials) uses an unlisted address; the drill shows address and corresponding account.
  • No account — username on no account (a configured login the server does not know, or a misconfigured partner).
  • Bad key — presented key matches no certificate stored for the user (drill: the fingerprint).
  • Key failures — repeated-key-failure notices, the counter before a lockout.
  • Locked — attempts while the user is “locked due to too many failed login attempts”; repeated lockouts deserve a look.
  • Auth failed — the anonymous Authentication failed using local. line (no username or address: whitelist passed, no evaluable credential). Counted for the login whose Allowed precedes it within one second (an Allowed consumed by its own authentication does not compete); two candidates = neither — a floor, not a total.
  • Session errors — Error/Warning [Ssh Default] lines of no other column (Stream read/write error. Exception message is: CMS parsing has failed and kin), attributed by session id.
  • Re-screens (last) — an Allowed on an already-authenticated connection: a partner holding a connection open re-keys about hourly, logging Start login process + Allowed user again without new authentication. Not in Allowed; neither attempt nor problem; never moves the row colour.
  • First / Last logon, Logons, Pattern — the detail pages’ logon summary: successful authentications over any protocol (Logons can exceed the SSH-only Authenticated; Never = never authenticated). Pattern = typical spacing (Continuous, Every 15 minutes, Hourly, Daily, Rarely…; Once = one visit, the spacing between two when too few for a median — a gap over 30 minutes starts a visit; Irregular = fewer than six gaps in ten within half and double the typical). Full-period under a date range.

Rules

  • Source: TM lines [Ssh Default] Allowed user 'U' from address 'IP' (Info), [Ssh Default] Disallowed user "U" from address "IP" , corresponding account "A" (Warning), [Ssh Default] User 'U' is locked. (Info) — one per screened attempt: log lines, not transfers; the date filter re-aggregates from per-day buckets.
  • Every line carries its SSH session id: an Allowed later than the session’s last successful authentication is a re-screen; an uncounted Error/Warning line is a session error of the login the session authenticated as.
  • Row colour = the login’s latest screening outcome, full-period: green = newest funnel line a successful authentication; red = anything else (a refusal, a failure, an Allowed no authentication followed — a re-screen is not one); orange = configured, never in the funnel. In a green row problem cells keep their red (Disallowed, No account, Bad key, Auth failed) or amber (Key failures, Locked).
  • Door knockers — the “not associated with any account” lines. Near misses: FE-namespace names (FE + digits), red, from a handful of addresses; Configured login = yes is the alarming case — defined in Flow Manager, mapped to no account (a provisioning gap or a decommissioned name). Scanners: the 25 most-tried other names (root, admin, user, test…) over many addresses, never past the account lookup, so in no other logon column; IPs = distinct sources; the total sums shown rows. Both also count unconfigured names rejected as Unable to find account with username: U, so an unknown name never sits among the configured logins. Source IPs stay full-period.
  • Successful logons per account and source IP — SSHD “successfully authenticated over SSH” lines, @endpoint stripped; Logins additive, Source IPs and Accounts distinct (full range). The certificate table counts “Authentication attempt with certificate” lines; Accounts on certificate = the accounts that serial is authorized for; above one (amber) = a shared key.
  • Outgoing — Authentication failure connecting to remote host H:P as user U: reason, one row per host/user: Password (wrong/expired), Key (publickey refused; also per host in the “Publickey authentication was cancelled/failed” table), Certificate (FTPS “530 Need certificate authentication” / “534 Policy requires valid SSL Client certificate”: the partner demands or rejects our TLS client certificate), Other (e.g. “530 User cannot log in”); last reason verbatim, first/last dates; 0 renders empty. A persistent row usually means an expired password, key or client certificate on our side.

Tips

  • Click an Incoming count for its 5 most recent lines (“date time  Level Component  message”, newest first); other rows expand to 10.
  • Logins, hosts and users known from the transfer logs link to their detail pages; a login’s Incoming connections table there judges the same addresses from the transfer-log side.
