Logon

What this shows

How the server screened each SSH logon: one row per login (the SSH username a partner connects with), the columns following the logon funnel. Allowed — the source address passed the account's AllowIP whitelist; Authenticated — the credentials passed too (logged for every account, whitelisted or not, so it can exceed Allowed); Disallowed — the address was rejected by the whitelist; No account — the attempted username exists on no account (probing or a misconfigured partner); Bad key — the submitted key matches no certificate in the user's store (the drill shows the offending fingerprint); Key failures — the server's repeated-key-failure notices, the counter that precedes a lockout; Locked — attempts blocked because the user account is locked; Auth failed — the platform’s anonymous failure line (Authentication failed using local., no username or address: a client that passed the whitelist and then failed without presenting an evaluable credential). It is attributed by timing — counted for the login whose Allowed line it follows within one second, an Allowed already consumed by its own successful authentication not competing — and a window holding two different candidate logins counts for neither, so the column is a floor, not a total. A login with disallowed entries means a partner (or someone using its credentials) is connecting from an address missing from the whitelist; the drill-down shows the address and, on the Disallowed lines, the corresponding account.

The last four columns are the login’s logon summary, the same figures as the detail pages’ Logons table: First and Last logon, the raw Logons count and the Pattern — the typical spacing (Continuous, Every 15 minutes, Hourly, Daily, Rarely…; 1 visit or 2 visits when there are too few visits for a cadence — a gap of more than 30 minutes starts a new visit). These count successful authentications over any protocol, so Logons can exceed the SSH-only Authenticated; a login that never authenticated reads Never. Unlike the funnel counts, the four keep their full-period values when a date range is selected.

Row colours. Every configured login is listed, and each row is tinted by the login’s latest screening outcome: green when its newest funnel line is a successful authentication, red when the newest line is anything else — a refusal, a failure, or an Allowed that no authentication followed — and orange when the login is configured but never appeared in the SSH funnel (every funnel column empty). The colour is a full-period verdict: a date range re-aggregates the counts but does not move it. Inside a green row the problem cells keep their own red (Disallowed, No account, Bad key, Auth failed) or amber (Key failures, Locked).

Click any count to expand that cell's 5 most recent log lines ("date time  Level Component  message", newest first). Login names link to their transfer-side detail page when one exists — its Incoming connections table shows the same addresses judged against the whitelist from the transfer-log side.

The report has two tabs. Incoming is the funnel table described above. Outgoing is the opposite direction of trust — this server failing to authenticate AT a partner's server (Authentication failure connecting to remote host H:P as user U: reason errors): one row per remote host/user pair with the failure count split into Password, Key, Certificate (the FTPS “530 Need certificate authentication” / “534 Policy requires valid SSL Client certificate” refusals — the partner demands or rejects our TLS client certificate) and Other (the residue), the last-seen reason verbatim and first/last dates; a persistent row usually means an expired password, key or client certificate on our side. Click a row for its 10 most recent log lines. (This table absorbed the former Failed logins report.)

How it's computed

The counts come from the server log's TM component: [Ssh Default] Allowed user 'U' from address 'IP' (Info) and [Ssh Default] Disallowed user "U" from address "IP" , corresponding account "A" (Warning) plus [Ssh Default] User 'U' is locked. (Info) — one line per screened logon attempt, so the figures count connection screenings, not transfers. The From/To date filter re-aggregates both counts per login from per-day buckets.

Door knockers splits the “not associated with any account” screening lines into near misses (FE-namespace names, red — the actionable rows, especially names configured in Flow Manager yet unknown to the server) and the scanner top 25 (root, admin, …).
