IO errors

What this shows

The platform failing to read (or write) a file on its own storage. The server log writes one line per attempt:

IO Error reading file /data/FlowManager/VDN@FE000436/25U_20260901T150913519_P00390030467_V000077_20260901_25R.xml

The path is the account's FlowManager folder — the landing directory a partner pushes into — and its name is account@login, so one line names the account, the login the partner used and the file. Nothing about the remote end is wrong: the connection worked and the upload landed. The platform then could not read the file back — a file deleted or moved while a route was running, a stale NFS handle, a slow or full volume, a permission on the folder.

The transfer log cannot show this on its own. The upload leg looks fine, and the route that failed to read the file writes no transfer row — the File simply ends one-legged (Failed) or, when a retry read the file, goes through as if nothing had happened. This report is the server log's side of that story, joined back to the Files it concerns.

The three tables

  • IO errors per folder — one row per FlowManager folder (account + login). IO errors counts lines, Files the distinct file names, Error / OK the distinct Files by their outcome (Waiting counts as OK, Expired as Error), Not logged the lines naming a file the transfer log never saw. Subscriptions lists the flows the joined Files belong to. Click a row for its 10 most recent lines.
  • IO error lines — every line, newest first. Operation is the wording between “IO Error” and the path (“reading file”), State the joined File's outcome — Failed: the route never read the file; Processed: a retry read it and the file went through; not logged: no File carries that name — and Transfer that File's own timestamp. The File cell opens the file's error page (or File page) when the site has one; the row expands to the verbatim message.
  • Per day — lines, folders and files per calendar day: a burst on one day is a storage incident, a steady trickle from one folder is that folder's problem.

How it's computed

Every server-log line carrying IO Error (as a word, any case) or Input/output error (the Java/POSIX wording of the same) is taken; the path is the first /… token after it and the folder its directory. A path outside a FlowManager folder is kept with an empty account, so nothing is dropped. Each line is then joined to the transfer log by file name: the File in flight at the time — the newest one starting before the error, else the first one after it — supplies the subscription and the outcome; when no File matches, the line's session is looked up in the transfer legs for the subscription alone. Account and login are shown in their configured spelling, so the cells link to the detail pages. Line and File counts are additive and re-total under the date filter.

Why it matters

An IO error is the platform's own storage misbehaving, and every flow whose folder sits on the same volume is exposed. A folder that logs them daily wants a look at the disk, the mount and the folder permissions; a one-day burst across many folders is an incident on the storage side. The Error column is the real damage — files a partner delivered that never went anywhere and were never reported back as failed by the transfer itself — while the OK column shows how often a retry papered over it. The same lines classify as IO error on the Failed transfers list and the home page's Reason column, and as their own bucket on Errors / Reasons and Per flow.
