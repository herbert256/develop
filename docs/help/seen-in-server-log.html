Seen in server log

What this shows

Some entities are alive on the server — they connect, authenticate, or are the target of a connection — yet never produce a record in the transfer log. The build marks such names blue in the FlowManager base result caches, so the entity, detail and coverage views can show them as server-log only. It does not create a File or transfer row, so File totals, day pages and per-transfer dimension reports remain based only on real transfer-log data.

The page opens with the two result-status rollups from the Flow manager Entities and Logical, Partners, Domains, Applications & BL analyses pages, followed by a Why blue attribution table, message shapes and the surviving server-log evidence tuples. Blue is an independent fourth result state: it means no real transfer exists for that entity. The blue discovery does not turn an entity with real red or green transfer health into another result. The evidence list counts surviving seed tuples, not distinct final blue names: one tuple can attribute several related entity types through the FlowManager cross-references, and the final result rollup can surface additional related blue names. Those totals are therefore different counting units.

  • Seed — which "Missing …" list supplied the evidence: account, login, subscription, host or whitelisted IP. Only Transfer Manager runtime messages qualify; deployment and housekeeping mentions do not mark an entity blue.
  • Account / Login / Subscription / Remote Host — the seed plus the entity values that the FlowManager cross-references can fill unambiguously. A truncated subscription spelling is canonicalized when it uniquely prefixes one configured name. Each populated cell links to that entity's detail page.
  • Date / Time — the seed's most recent qualifying server-log mention. Click the row to expand that message (truncated to 300 characters), which is the evidence for the server-log sighting.

How it's computed

bin/build/seen-in-server-log.sh runs after the two log parses and before the normal result fill. It reads the data/unknown/ sidecars, enriches each qualifying seed through the FlowManager cross-reference caches, writes the server-log evidence sidecars, and marks names blue in data/flow-manager/base/ only when no real File carries that entity. It never changes _files.tsv or _transfers.tsv. A host seed with no configured attribution is dropped; a whitelisted-IP seed whose partner already has real transfer data is not treated as a new server-only discovery; duplicate enriched tuples collapse. The later result step preserves valid blue names, derives related partner/application/domain and SSH-logon blue results where appropriate, and can deliberately mark a would-be-blue UC3 subscription green when the server log proves a clean poll that simply found no file.

About this report

Entities that appear in server-log runtime messages (Transfer Manager lines) but have no record in the transfer log are marked blue — a 4th result state — in the base result column (build step `bin/build/seen-in-server-log.sh`), so they surface in the entity reports, detail pages and coverage views as *server-log only* (the Server bucket) with no fabricated transfer. This page is the audit of that step: 53 entities are currently marked blue, every one accounted for in the Why blue matrix below. The TM-message seeds materialized 18 injected tuples — 4 from account seeds, 0 login, 12 subscription, 0 host, 2 whitelisted IP; an entity discovered only by its successful SSH logons (the logon rule — no TM tuple exists) is claimed Direct in the matrix with the logon line as its evidence. The two tables below are the result-status rollups from the Flow manager Entities and Logical, Partners, Domains, Applications & BL analyses pages (Seen = configured entities with at least one transfer OR a blue server-log sighting; Error / Warning / Ok = red / orange / green by each seen entity's last transaction); a (+n) or (−n) on a figure is how much the blue marking moved it — the Seen column gains the blue count, and the entities leave Warning (they are no longer *never seen*). In the list, each entry is two rows — the server-log message that proved the entity alive, then its blue attribution: the seed plus everything the FlowManager cross-references could unambiguously fill in (a truncated subscription name is canonicalized to the configured name it uniquely prefixes). A host or whitelisted-IP seed that ties to no account, login, subscription or flow is dropped — as is a whitelisted-IP seed whose partner already has transfer data (an unused alternate address is not a server-log discovery) — and two seeds enriching to the same entity combination collapse into one row.

Why each blue entity is blue — every entity is counted exactly ONCE: under Direct when its own name appears in its type's server-log seed list (the raw sightings, before duplicate seeds collapse) OR when only its successful SSH logons discovered it (the logon rule — no TM tuple exists; its evidence line is the logon), otherwise under the seed type of the first surviving seed tuple that reached it through the FlowManager cross-reference enrichment (later seeds reaching an already-claimed entity are skipped). Logical, Partners, Domains, Applications and BL are derived attributions — never a TM seed themselves, so a Direct entry there is an SSH-logon-era rollup discovery. Total = the sum of the other columns = the type's blue entities. Every nonzero cell links a page listing the entities it counts with their claiming server-log lines.

The seed's latest server-log message, grouped into shapes: quoted values, IPs, UUIDs and numbers are normalized away so like events cluster. Click a shape to jump to its own injected-transfers table below. Click a column header to re-sort.

One table per message shape (most frequent first). Each entry is two rows: the seed's most recent server-log line (the one the blue marking is dated to; truncated to 300 characters), then the entity's blue attribution. No transfer is fabricated — the entity is simply marked blue (result = blue) in the base result column, so the per-row dimension reports (protocol, AV scan, ciphers, …) never see it and only the entity, time and coverage views count it (in the Server bucket).
