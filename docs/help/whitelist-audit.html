Whitelist audit

What it shows

The partner AllowIP whitelists against what actually connects: the site-wide roll-up of what the per-partner detail pages’ tables cannot show.

Sections

  • Active whitelisted addresses — the entries doing work: Used carried real Files; Connects only shows server-log connections but no transfer (something connects and never delivers — worth a look).
  • Unused whitelist entries per account — the whitelist is the expanded AllowIP list (CIDR ranges explode into many member addresses), so unused entries aggregate per allowing account instead of thousands of rows. A red row’s whitelist is entirely unused.
  • Sources without a whitelist entry — addresses that carried traffic with no entry at all. Internal cluster addresses appear here legitimately (PeSIT needs no whitelist entry); an unexpected external address is the row to chase.

Rules

  • Whitelist from the config caches; observed Files from the transfer logs’ inbound source addresses; connection counts from the server Inbound Connections report.
  • A named (non-IP) source is an address the parse already resolved to its hostname.
  • Every unused entry is attack surface that buys nothing; every unlisted source that connects means a broader policy (or an internal path) is doing the admitting.
