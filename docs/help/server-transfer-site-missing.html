Transfer site missing

What it shows

One row per endpoint where SecureTransport ran a transfer with no transfer site in its environment and fell back to the communication profile’s raw host, port and user — the warning Transfer site ID is not present in environment. Using host, port and user: host:port:user.

Columns

  • Host — the endpoint the fallback connected to, linked to its detail page.
  • Warnings — how many times it happened.
  • Users / Ports — the other fallback values, read from the message. Several users on one host: several profiles share the endpoint and more than one lost its site reference.
  • First / Last — the window the warnings span. A tight burst is a change that went wrong; a long tail a gap nobody noticed.

Rules

  • The transfer still moves, so this is a configuration gap, not a runtime failure: a route or profile that lost its transfer-site reference. Cost: the connection runs on profile values alone — no site-level routing, no site-level limits.
  • Rows are hosts because the message is the one server-log line that names no flow: neither it nor its session mentions a subscription. A host appears once however many flows use it.
  • A host that moved a file OK since its newest warning is not listed — a later OK transfer through the endpoint says the gap is closed (the “recovered since” test of Deploy errors); the intro says how many hosts that cleared.
  • These are Warnings: the colour rules (bin/build/result.sh) redden a host on unattributable Errors only, so they count against no subscription and live on this page.

Tips

  • Click a row for its 10 most recent warnings.
  • Deploy errors covers the configuration defects that stop a flow (an abandoned route, a profile that cannot receive); this page the one that quietly degrades it. The polling tables are on the UC status / UC3 tab.
