Trouble after Success

Subscriptions whose last transfer was OK but which then logged a server-log error or warning — a flow that last looked healthy but has since run into trouble.

What this shows

One row per subscription whose last transfer was OK but which then logged an Error in the server log after that transfer — either the subscription itself, or a connected login, account or remote host. Errors only: a Warning does not put a flow here — the warnings-only shape was the benign Transfer site ID is not present in environment, which has its own Transfer site missing report. It is the fleet-wide view of the same "errors after last transfer" signal the per-subscription detail pages flag with a red banner: a flow that last looked healthy but has since run into trouble.

Still-green flows only. That same evidence is what turns a subscription red site-wide, so one this page would otherwise name that has already gone red is not an early warning any more — it is simply failing, and the home page lists every red flow with the reason beside it. The intro says how many were left out for being red already. Since 2026-08 this evidence itself turns the flow red (the trouble-after-success flip): a flow with a post-delivery error goes red and onto the home page’s Failing subscriptions in Server log table — unless its newest error is a deploy defect (those stay with the Deploy errors report, and the flow stays green here), or a UC3 has polled cleanly since (cleared, healthy). What is left on this page is therefore small by design: the deploy-classified and poll-cleared flows whose errors did not redden them.

Columns: the Subscription (linked to its detail page), its Last OK transfer (date and time), the count of Errors logged after it, the Latest error (that line's date and time), the Source (which entity logged them — the Subscription, its Account, its Login and/or its remote Host), and the Latest message. Click a row to expand its 10 most recent Error lines.

How it's computed

The last transfer per subscription (and whether it was OK) comes from the transfer cache — the most recent logical transfer for that subscription and its delivered outcome. The Error lines come from the server log's per-name caches for the subscription and its configured login(s), account(s) and remote host (the connections from the FlowManager configuration); only E-level lines dated after the last transfer are counted, deduplicated across caches — Warnings are ignored. The host ring joins only where the subscription has exactly one configured host, and it carries the addresses that endpoint resolves to as well — the same restriction the site’s result colours use, so a flow this evidence turns red is a flow this page can name. A host serves other flows too, which is why the Source column says where a line came from. The scheduler poll-backlog warning (… Skipping the next scheduled occurrence of this task.) is deliberately excluded — it is routine backlog, not a failure.

The counts are full-period (this page is not narrowed by a date filter). A subscription appears only when its last transfer was OK, at least one Error followed it, and its result colour is still green; a subscription whose last transfer already failed is covered by the ordinary failure reports, not here.

Why it matters

A subscription that transferred successfully and then started logging errors or warnings is an early sign of a problem that the transfer counts alone won't show — the next transfer may not have been attempted yet, or the trouble is on a connected login/account. Because a connected account serves other flows too, an account-sourced Error/Warning need not concern this exact subscription; the Source column tells you where it came from, and the drill shows the messages so you can judge.
