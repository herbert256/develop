Connection efficiency

What it shows

How the technical connections are used. A session is one connection — an SFTP login, a PeSIT session — identified by the log’s Session ID column; it can carry many Files, but here mostly carries one. The intro gives sessions, Files, Files per connection, the single-File share and the User- vs Server-initiated split.

Sections

  • Files per connection — per account: sessions, Files, ratio; least efficient first. 1.00 = a fresh connection per File; at tens of thousands of sessions batching would cut real overhead.
  • Connection storms — per account: the most sessions started inside one minute (Peak) and when; Sessions = its whole-window total.
  • Failing sessions — All-Error, Mixed OK+Error and Retry marathons, with platform-wide counts.

Rules

  • A session belongs to the account of its first record; records without a usable Session ID are excluded (count in the intro).
  • The league lists User-initiated sessions only (first record’s Action By = User: the partner controls the reconnects), accounts with 200+ such sessions. The TOTAL row is the whole platform, any initiator, so it exceeds the listed sum.
  • Storms count any initiator; Peak is a maximum, not additive. A three-digit peak is a client script opening a connection per file: harmless for one partner, a load spike and noisy-neighbour risk on shared listeners.
  • All-Error = 2+ records, all failed (a connection that achieved nothing). Mixed OK+Error = some Files delivered, others failed. Retry marathons = 8+ records, one File, all Error.
  • Failure anatomy uses per-record status (OK = raw Status Processed), not the per-File outcome.
