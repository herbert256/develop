Deploy errors

What this shows

Accounts and subscriptions a configuration defect stops dead — and that have not had a successful transfer since. Two server-log lines qualify, both a deployment mistake rather than a runtime fault; the Cause column says which put a row here.

1. The route was abandoned

The Advanced Routing step error ARSP0001:

[<account>] [<subscription>] An error occurred while sending the file {…} to a partner site. Step configuration suggests to stop further route execution.

The distinction that matters: the step did not merely fail. Its configuration told SecureTransport to abandon the rest of the route, so nothing downstream ran for that file — no onward delivery, no follow-up step. A flow can sit in this state indefinitely while looking quiet rather than broken.

2. The profile cannot receive

The PeSIT line Transfer profile '<P>' of account 'SECURETRANSPORT' is used for incoming transfer, but 'Receive File As' field not set. — one field never filled in on the transfer profile, and every incoming transfer of that flow errors because of it. The same shape as the first: configured wrong, so nothing gets through.

The row names the subscription the profile belongs to, resolved through the configuration. The message itself names only the platform’s own SECURETRANSPORT account, and a transfer profile is internal flow plumbing with no page of its own — so it is never listed as an entity, and a profile matching no single configured flow is left out rather than guessed. Config hygiene lists the same defect per profile, including the ones that have since recovered.

The columns

  • Account or subscription — the entity the line names. Normally the account; the subscription where the line names the platform's own SECURETRANSPORT account, which is blacklisted everywhere else on the site and would make a useless row. An account's @FE… endpoint suffix is stripped, as the transfer parse strips it, so the name links to its detail page.
  • Type — which of the two it is.
  • Cause — which line put the row here: Route stopped, Receive File As not set, or both when an entity has each.
  • Messages — how many such lines that entity has. A high count is a flow retrying into the same wall.
  • Last message — the most recent one. Rows are newest first.

Why the list is shorter than the log

Only unresolved entities appear. If an OK File arrived after an entity's last such message, something has got through since and the row is dropped — it is history, not a live problem. A UC3 subscription is also cleared by a successful poll after its last message, even one that found no files: the listing works again, so the stopped route is history. The comparison is exact to the millisecond, so a recovery on the same day still clears it.

That is the same rule the Connection failures box uses, and it is what makes this page a worklist: in acceptance it cuts 118 entities carrying a message down to the 33 that are still stuck.

How it relates to the other pages

This page isolates the one routing outcome that abandons a route. Connection failures covers connections that never got established at all, and the entity's own detail page carries its recent server-log lines in full.
