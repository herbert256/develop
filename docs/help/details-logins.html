Login Details

What it shows

One page per login name, linked from every Login cell across the site.

Sections

  • KPI line — rank and share among all logins, failure rate, volume, cadence, processed-transfer performance where a duration is recorded, and (like accounts) a distinct session count.
  • Features and Waiting/Expired — side by side at the top. A single-row Partner, Application, Domain or Logical breakdown is folded into a Features row, keeping its link and colour.
  • Activity per day row — with Logons and Incoming connections beside it; without transfer data (blue and never-seen logins) the row is Features, Logons, Incoming connections. Then Activity per week / hour / weekday.
  • Subscriptions breakdown, Last error(s) directly under it, then Accounts; further breakdowns: remote host, protocol, AV scan, security parameters, direction, action-by, mode.
  • Last error(s) — only when a subscription it moves files with has an error: one row per such subscription, its most recent error, newest first — date and time, subscription, file. Red = failed, orange = expired before the partner collected it.
  • 10 largest transfers.
  • Whitelisted IPs — when the login’s partner carries an AllowIP whitelist (partners.json): the source addresses allowed to connect with this login; the whitelist belongs to the partner account owning the login. Configuration, not activity: the date filter leaves it unchanged.
  • Last server log messages — at the very bottom: its 25 most recent lines merged with its 10 most recent Error/Warning lines, plus the Error/Warning lines of its 1-to-1 connected entities (its one account, subscription, host) after the login’s last transfer. Deduplicated, newest first, full-period.
  • Any such after-the-last-transfer line raises the red top banner ERRORS IN SERVER LOG AFTER LAST TRANSFER – SEE LOG AT BOTTOM OF THIS PAGE.

Logons table

  • A logon = a successful authentication in the server log, any protocol. Rows: the first logon, how many (newest in Last), the pattern.
  • Pattern = the typical spacing, in the UC2 Pickup pattern vocabulary: Continuous, Every 15 minutes, Hourly, Daily, Weekly, Every N hours/days, Rarely; Once for a single visit, the spacing between two when too few for a median; Irregular when fewer than six in ten gaps fall within half and double the typical spacing.
  • A gap over 30 minutes starts a new visit; a burst of connections seconds apart is one visit, so the pattern says how often the partner comes, not how many connections a visit opens.
  • These rows appear only for a login that has logged on; a login moving files without them connects in a way that logs no authentication line (CFT/PeSIT-side transfers).
  • Below them the SSH screening-funnel counts, row for column as the Logons / Incoming server report: Allowed, Disallowed, Authenticated (SSH only; shown only when it differs from the any-protocol count above), No account, Bad key, Key failures, Locked, Auth failed.
  • Auth failed = the platform’s anonymous Authentication failed using local. line, attributed to the login whose whitelist-Allowed it follows within a second.
  • Two session-keyed rows can follow: Re-screens (an Allowed on a connection that had already authenticated — the hourly re-key of a kept-open connection, not a logon attempt) and Session errors (the Error/Warning SSH lines of its sessions, red).
  • Each funnel row’s Last is its newest occurrence: an old Bad key beside fresh Key failures is a problem that changed shape.
  • Zero rows are not shown: a clean login shows only Allowed; only funnel rows = a login that knocks (or is knocked for) without getting in; no logon evidence at all = no table.

Rules

  • Every count is in Files, as distinct (login, CoreId) pairs: a File touching several logins counts once on each login’s page.
  • The account / subscription / remote host tables are cross-referenced with the FlowManager configuration: every partner configured for this login is listed — green = logged data; red = configured, never seen with it (no counts, a link to its never-seen page). Partners logged but not configured are listed too (green).
  • Narrowing the date filter re-tints: a partner without activity in the range turns red instead of being hidden.
  • Every configured name from the FlowManager exports has a page. Background: light brown = seen & in, light blue = seen & out, light gray = seen & both/unknown, light yellow = never seen & in, light orange = never seen & out, light purple = never seen & both/unknown.
  • A never-seen page opens with a “configured, never seen” line, its configured cross-references (all red) and any whitelisted IPs.
  • Configured both ways: every outcome splits into In - Error / In - OK / Out - Error / Out - OK by each file’s own direction; a file without a direction counts in Files and Volume only.

Tips

  • Click anywhere on a Last error(s) row (name included) for the file’s error page: every leg plus the server log of the failure — the files of the Failed Subscriptions list, which guarantees every subscription’s last error has a page.
