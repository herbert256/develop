Login Details

What this shows

The per-login detail page — one real page per login name (linked from every Login cell across the site). It opens with a KPI line, then Activity per day/week/hour/weekday, a breakdown of every other dimension this login's transfers touch (account, subscription, remote host, protocol, AV scan, security parameters, direction, action-by, mode), and the 10 largest transfers seen for it.

When the login's partner carries an AllowIP whitelist (partners.json), a Whitelisted IPs table at the bottom lists the source addresses allowed to connect with this login — the whitelist belongs to the partner account that owns the login. Configuration, not activity: the date filter leaves it unchanged.

The account / subscription / remote host tables are cross-referenced against the FlowManager configuration: every partner configured for this login is listed, whether it appears in the logs or not. Green rows have logged data; red rows are configured but never seen with it — they carry no counts but do link to that name's own (never-seen) detail page. Partners logged without being configured are listed too (green). Narrowing the date filter re-tints the rows: a partner with no activity in the selected range turns red instead of being hidden.

At the very bottom a Last server log messages table shows the tail of the server log for this login: its 25 most-recent lines merged with its 10 most-recent Error/Warning lines, plus the Error/Warning messages of its 1-to-1 connected entities (its one account, subscription, host) that occurred after the login's last transfer. If any such after-the-last-transfer Error/Warning exists, a red banner appears at the top: "ERRORS IN SERVER LOG AFTER LAST TRANSFER – SEE LOG AT BOTTOM OF THIS PAGE". Deduplicated, newest first, full-period.

The Logons table

Beside the Activity per day table (with Incoming connections as the third table of that row; on a page without transfer data — the blue and never-seen logins — the row is Features, Logons, Incoming connections instead), a Logons table sums up this login’s authentications: the first successful logon, how many there were (the newest one in that row’s Last column), and the pattern — the typical spacing between them, in the same vocabulary as the UC2 Pickup pattern (Continuous, Every 15 minutes, Hourly, Daily, Weekly, Every N hours/days, Rarely). A logon is a successful authentication in the server log, over any protocol; bursts of connections seconds apart read as one visit, so the pattern tells how often the partner comes, not how many connections a visit opens. The four rows appear only for a login that has actually logged on; a login the server log never saw authenticate skips them — on a login that moves files anyway, that means the partner connects in a way that logs no authentication line (CFT/PeSIT-side transfers).

Below those four, the table lists this login’s SSH screening-funnel counts — the same figures, row for column, as the Logons / Incoming server report: Allowed, Disallowed, Authenticated (SSH only — shown only when it differs from the any-protocol logon count above), No account, Bad key, Key failures, Locked and Auth failed (the platform’s anonymous Authentication failed using local. line, attributed to the login whose whitelist-Allowed it follows within a second). Each funnel row’s Last column carries the newest occurrence of that event, so an old Bad key next to fresh Key failures reads as a problem that changed shape. A zero row is simply not shown, so a clean login shows nothing beyond its Allowed count — a table holding only funnel rows is a login that knocks (or is knocked for) without ever getting in, and a login with no logon evidence at all has no Logons table.

Last error(s)

Directly below the Subscriptions table, a page carries a Last error(s) table whenever any subscription it moves files with has something wrong on it: one row per such subscription — its most recent error, newest first — with the date and time, the subscription and the file. Rows are tinted by kind, red for a failed file and orange for one that expired before the partner collected it, and there is no table at all when nothing connected to this entity has an error.

Clicking anywhere on a row — the subscription name included — opens that file’s error page, with every transfer leg and the server log of the failure. Those are the same files the Failed Subscriptions list holds: that page guarantees every subscription’s last error has a page, which is what lets this table link straight to it.

Direction, page colors and never-seen pages

Every configured name from the FlowManager exports has a page — seen in the logs or not — and the page background color says the same at a glance: light brown = seen & in, light blue = seen & out, light gray = seen & both/unknown, light yellow = never seen & in, light orange = never seen & out, light purple = never seen & both/unknown. A never-seen page opens with a "configured, never seen" line and shows the configured cross-references (all red) and any whitelisted IPs.

An entity configured both ways splits every outcome into four columns — In - Error / In - OK / Out - Error / Out - OK — by each file's own direction; a file with no direction of its own counts in Files and Volume only.

When a page carries both green (logged) and red (configured-only) rows, the tint tells them apart at a glance. The page opens with Features and Waiting/Expired side by side, then the Activity per day row; the Subscriptions breakdown follows (with Last error(s) directly under it), then the Accounts breakdown.

How it's computed

The KPI line adds this login's rank and share among all logins, failure rate, volume and cadence, processed-transfer performance where a duration is recorded, and (like accounts) a distinct session count. Every count on the page is in Files, counted as distinct (login, CoreId) pairs — a File touching several logins counts once on each login's page.

A Partner, Application, Domain or Logical breakdown holding exactly one row is folded away: the name appears as a row in the Features table instead, keeping its link and colour.
