UC3 status — polling partners

What it shows

The one report about us polling partners, five tables on one tab: UC3 status (every configured UC3 subscription — we connect out on a schedule and fetch what is waiting — in one of six statuses, the info boxes counting them), then Polls by subscription and Remote directory listing failures, then Configured cronjobs and Schedules that never complete a poll.

Siblings: UC1 (we push out), UC2 (the partner collects from us), UC4 (the partner delivers to us).

Status columns

  • Status — one of six, a complete partition (below). Subscription — the configured name, linked to its detail page.
  • Files / OK / Error / Last file — Files pulled in, by outcome, and the newest one’s date (_files.tsv); zero on a blue row.
  • Polls / Empty polls — poll results and how many found nothing; a high empty count is normal.
  • Problems — a connection failure or a failed directory listing.
  • Last log — the newest line of any counted kind, the ones that merely prepare a poll included: “still running at all”. On a server - error row it can be newer than the failures — the flow still polls, it last failed earlier.

Statuses

  • ok (green) — its latest File was delivered. error (red) — the latest failed, no OK File in the window: nothing ever worked. ok -> error (red, was green) — OK Files before: a regression.
  • server - no files (blue) — the last poll found zero files: connection, credentials and directory fine, nothing on the other side (No remote files).
  • server - error (blue) — the log’s latest word is a Connection failure or an Error occurred while listing files (No remote dir, the polls tables).
  • server - no result (blue) — only the “Remote folder of transfer site … evaluated to …” lines that set a poll up, then neither result nor error.
  • not seen (orange) — configured, in neither log; box and rows absent when there is none, so a subscription can never drop out silently.

Status rules

  • Roster: every UC3 name in the FlowManager export, run or not. Colour = the site-wide result: green/red real transfer data (the LAST File OK / Failed-or-Expired), blue server log only.
  • error vs ok -> error is per File — right after any OK File the subscription WAS green — finer than From green to red, which buckets by whole days and misses a flow failing at the end of every day.
  • The blue split takes the most recent decisive line (latest-wins, not any-failure): most blue flows carry empty polls and an occasional failure (one polls 8,941 times, fails 24); the newest line is where the flow stands, the rule the colour follows. A poll that found files decides neither status.
  • Current-state: the date filter narrows only the two poll tables; the status and cron tables are full-period and show the badge when a range is set.
  • Click a row for its 10 most recent server-log lines; on a server - error row the failures, which thousands of routine poll lines would bury.
  • A UC3 fails quietly — an empty directory and a partner that stopped delivering look alike, and neither writes a transfer record: chase the partner (no files), fix connection or path (server - error), find why a started poll never reports (no result).

Polls by subscription and listing failures

  • Source: Applying the search pattern '<pattern>' for transfer site '<SITE>': N file(s) were found of which M matched the pattern. Per subscription: polls, empty polls (M = 0), files matched, empty %; worst first.
  • Only that line is used — the bare “No files were found for download.” lines name no site. The site is truncated at _SCP_ to the clean name and shown as logged; a name matching a known subscription links to its detail page (a chronic empty poller may have none).
  • Listing failures: “Error occurred while listing files from partner <SITE>” — the folder could not be listed at all (wrong remote path, permissions), unlike an empty poll; concentrated on a few subscriptions.
  • Additive; both re-total under the date filter. Click a subscription for its 10 most recent lines.
  • An empty poll costs a slot, a connection and a listing, moves nothing and leaves no trace in the transfer log. A very high empty rate: a schedule far more frequent than the source produces, or a source that stopped.

Configured cronjobs

  • The polling schedules in the FlowManager subscriptions.json; each belongs to a UC3 subscription (SecureTransport is the client). Inbound flows are event-driven, never here; UC1 pushes on directory scanning — no cron. All enabled, none skip holidays.
  • Subscription · Protocol (SFTP or FTP) · Cron expression (raw, to cross-check with FlowManager) · Schedule (plain English, computed at build, always in sync) · Polls / Active days (poll lines, days with life) · Observed.
  • Rows tinted by result: green OK, orange never seen, red Error, blue server-log only.
  • Quartz cron, six fields seconds minutes hours day-of-month month day-of-week: 0 0/15 * ? * * every 15 minutes; 0 0,30 8-17 ? * MON-FRI every 30 minutes on workdays 08:00–17:00; 0 0 4 ? * * daily at 04:00; 0 5 * ? * MON-FRI hourly at :05 on workdays.
  • Observed = when the schedule really fires, from the poll lines above: the median of each day’s first poll ± one standard deviation (first and last active day left out — the export window cuts into both); a poll rate for a schedule firing more than 3× a day. Matching is name-prefix, both ways.
  • · files = no poll lines, only the file arrivals give a slot (the Punctuality model); - = no poll and no File in the loaded logs — never fires.
  • Dark red Observed contradicts the schedule: the slot is off the scheduled time, the rate more than 3× off the expected one, or a continuous schedule is seen only a few times a day.

Schedules that never complete a poll

  • Every schedule whose Observed is -. Most do fire — Poll starts counts their “Remote folder / files pattern … evaluated” setup lines, right on the scheduled minutes — but the poll dies before the listing.
  • What goes wrong = the dominant failure line: a connection timeout, an SSH/TLS handshake failure, a password or public-key authentication failure, or a listing error such as “No such file” (login works, remote directory missing). Failure lines counts them all.
  • Connection and listing failures name the subscription; authentication failures name only host and user, so they match through the configured host and can be shared between flows on that host.
  • Neither starts nor failure lines = never fires at all in the loaded logs. Same server-log pass as the Polls table.
