UC3 status — polling partners

Since 2026-09-05 this tab is the one report about us polling partners. It carries five tables: the UC3 status table described first, then the Polls by subscription and Remote directory listing failures tables (the former Remote polls report, below), then Configured cronjobs and Schedules that never complete a poll (the former Cronjobs page, below). The date filter narrows only the two poll tables; the status and cron tables are current-state and show the full-period badge when a range is set.

What this shows

Every configured UC3 subscription — the pull use case, where we connect out to the partner on a schedule and fetch whatever is waiting — in exactly one of six statuses. It is one of a set of four: UC1 status does the same for the flows we push out to the partner, UC2 status for the ones the partner collects from us, and UC4 status for the ones the partner delivers to us. The info boxes above the table give the count per status. One row per subscription:

  • Status — one of six, a complete partition (see below).
  • Subscription — the configured name, linking to its detail page.
  • Files / OK / Error / Last file — the transfer-log history: logical transfers pulled in, split by outcome, and the date of the newest one. All zero on a blue subscription, which by definition has never appeared in the transfer log.
  • Polls / Empty polls — server-log poll results for this subscription, and how many of them found nothing. A working flow polls far more often than it finds files, so a high empty count is normal, not a fault.
  • Problems — server-log lines saying we could not retrieve: a connection failure, or a directory listing that failed.
  • Last log — the newest server-log line of any counted kind, the ones that merely prepare a poll included. It answers "is this flow still running at all", so on a server - error row it can be newer than the failures the drill shows: the flow still polls, it just last failed earlier.

The six statuses

The first three are the transfer-log verdict, read off the subscription's site-wide result colour:

  • ok (green) — its latest File was delivered. The flow is working.
  • error (red) — its latest File failed and it has never once delivered an OK File in the window. Nothing here ever worked, which points at the configuration or a partner side that was never finished rather than at something that broke.
  • ok -> error (red, was green) — its latest File failed, but it has delivered OK Files before: a regression. Something that used to work stopped, so there is a change to find.

The other three split the blue subscriptions — seen in the server log, never once in the transfer log — by what that log says about them. A blue subscription has no transfer history at all, so its poll lines are the only evidence there is:

  • server - no files — its last poll reported zero files found. The connection, the credentials and the remote directory are all fine; there is simply nothing on the other side. No remote files covers these in depth.
  • server - error — the log's latest word is that we could not retrieve: a Connection failure reaching the partner, or an Error occurred while listing files once connected. See No remote dir and Remote polls.
  • server - no result — the poll is only ever prepared: the log carries the "Remote folder of transfer site … evaluated to …" lines that set a poll up, and then neither a result nor an error. The flow starts and says nothing about how it ended.

A seventh status, not seen, exists for a subscription that is neither green, red nor blue — configured, but never observed in either log. Neither environment currently has one, so neither its box nor any row appears; it is there so a subscription can never silently drop out of the table.

How it's computed

The roster is every UC3 name in the FlowManager subscription export, so a subscription appears whether or not it has ever run. Green/red/blue is the site-wide result colour; Files/OK/Error come from the transfer cache (_files.tsv), and the poll signals from the server parse cache.

error vs ok -> error is a per-File question, not a per-day one: right after any OK File the subscription was green, so a red subscription with even one OK File in the window counts as a regression. That is deliberately finer than From green to red, which buckets by whole days and so misses a flow that fails at the end of every day while still delivering within them.

The blue split takes the most recent decisive line — a poll result of zero files, or a failure. It is latest-wins rather than any-failure-wins because most blue subscriptions carry both signals: 27 of acceptance's 71 have empty polls and failures, and for nearly all of them the failures are a 0.1–8% blip on a flow that otherwise polls perfectly well (one polls 8,941 times and fails 24). Counting any failure would call all 27 broken; a threshold would be arbitrary. The newest line is simply where the flow stands now — the same rule the green/red colour itself follows. A poll that did find files decides neither status, so a subscription with nothing else lands in server - no result.

This is a current-state audit, so the date filter does not narrow it. Click a row for its 10 most recent server-log lines — on a server - error row those are the failures, which would otherwise be lost among thousands of routine poll lines.

Why it matters

A UC3 flow fails quietly. A poll that connects and finds nothing looks exactly like a poll that finds nothing because the partner stopped delivering, and neither writes a single line to the transfer log — which is why two thirds of these subscriptions are blue and invisible on every transfer report. Splitting them by what the server log last said turns that silence into three different questions: chase the partner (no files), fix the connection or the path (server - error), or find out why a poll that starts never reports (server - no result). The red pair is the same triage on the flows that do reach the transfer log: ok -> error has a change to find, error probably never worked at all.

Polls by subscription and listing failures

The two tables that were the Remote polls report until 2026-09-05.

What they show

Many subscriptions work by polling a remote folder on a schedule and downloading whatever files are waiting. Each poll logs Applying the search pattern '<pattern>' for transfer site '<SITE>': N file(s) were found of which M matched the pattern. This report rolls those up per subscription: how many times it polled, how many of those polls picked up nothing (M = 0), how many files it did match, and the empty-poll percentage — sorted worst-first so the chronic empty pollers surface at the top.

A second table, Remote directory listing failures, is a different problem: "Error occurred while listing files from partner <SITE>" — the poll couldn't even list the remote folder (usually a wrong remote path or permissions), as opposed to an empty poll where the folder is correct but has no files. These are almost always concentrated on a handful of subscriptions.

How they are computed

Only the "Applying the search pattern …" line is used, because it carries both the subscription and the file counts. (The bare "No files were found for download." lines are ignored — they name no site, so they can't be attributed.) The logged site keeps its _SCP_… suffix; it's truncated at _SCP_ to the clean subscription name and shown as logged (mono, not linked) — a subscription that only ever polls empty may never appear in the transfer logs at all, so there's no detail page to link to. A poll counts as empty when zero files matched the pattern.

Polls, empty polls and matched files are additive and re-total under the date filter. Click a subscription to expand its 10 most recent poll lines.

Why they matter

An empty poll consumes a scheduled slot, a connection and a directory listing, but moves no data and leaves no trace in the transfer logs — so a subscription that polls thousands of times and never finds a file is invisible everywhere else. A very high empty-poll rate usually means the schedule is far more frequent than the source actually produces, or the source has stopped producing entirely; either way it's wasted work worth reviewing. Contrast this with Scheduler Overruns, which is the opposite failure — a poll that runs too long rather than one that finds nothing.

Configured cronjobs

The two tables that were the analyses Cronjobs page until 2026-09-05.

What they show

The polling schedules configured in the FlowManager subscriptions.json export. Every schedule belongs to a UC3 subscription, where SecureTransport is the client: it connects out to the partner’s server on a timer and pulls whatever files are waiting. (Inbound flows — where the partner connects into SecureTransport — are event-driven, not scheduled, so they never appear here.)

The columns

Subscription — the configured subscription name. Protocol — SFTP or FTP, whichever endpoint the schedule polls. Cron expression — the raw schedule as stored in the config. Schedule — that expression translated to plain English.

The cron expression

SecureTransport uses Quartz cron expressions, which have six fields: seconds minutes hours day-of-month month day-of-week. A few examples:

  • 0 0/15 * ? * * — Every 15 minutes.
  • 0 0,30 8-17 ? * MON-FRI — Every 30 minutes on workdays between 08:00 and 17:00.
  • 0 0 4 ? * * — Daily at 04:00.
  • 0 5 * ? * MON-FRI — Every hour at :05 on workdays.

The English translation is computed deterministically from the expression when the site is built — there is no external service and no cost involved, so it is always in sync with the configured schedule.

Notes

Every schedule listed is enabled, and none are configured to skip holidays. The number in the Schedule column is what the timer will actually do; the raw expression is kept alongside it so it can be cross-checked against the FlowManager configuration. Type in the search box to find a subscription; click a column header to sort.

Observed

The Observed column (merged from the former Schedule vs reality page, then the Cronjobs page) says when the schedule actually fires: it comes from the server log’s poll lines via the Polls by subscription table above — the median of each day’s first poll, ± one standard deviation (the first and the last active day left out — the export window cuts into both), with a rate shown instead for schedules firing more than 3× a day; slots marked · files fall back to the file arrivals (the Punctuality model). A dash means no poll and no File in the loaded logs — the schedule never fires. Polls and Active days count the server-log poll lines and the days the flow showed life. A dark red Observed cell contradicts its schedule: the observed slot sits off the scheduled time, the poll rate is more than 3× off the expected one, or a continuous schedule is only seen firing a few times a day.

Schedules that never complete a poll

The bottom table diagnoses every schedule whose Observed column shows a dash. Almost all of them do fire — their setup lines (“Remote folder / files pattern … evaluated”) appear in the server log right on the scheduled minutes, counted as Poll starts — but the poll then dies before the file listing that would count as a completed poll. What goes wrong shows the dominant failure line: a connection timeout (the partner endpoint is unreachable), an SSH/TLS handshake failure, a password or public-key authentication failure, or a remote listing error such as “No such file” (the login works but the configured remote directory is missing). Connection and listing failures name the subscription in the log; authentication failures name only host and user, so they are matched through the subscription’s configured host and can be shared between flows polling the same host. A row with neither starts nor failure lines never fires at all in the loaded logs.
