Subscriptions (analyses)

What this shows

Every configured FlowID (the customAttribute_FlowIdentifier value) on one row — the whole configuration mapping at a glance, still ordered by use case. A flow’s UC subscriptions share one FlowID, so they fold into a single row whose every cell is the union of their values. Then the derived Logical group (the FlowID condensed into its logical flow group), the account it belongs to, the derived Partner, Domain and Application groups, its endpoint (the login the partner connects in with — inbound — or the remote host we dial out to — outbound) and the BL tag — a full entity of its own, so the cell links its detail page.

Every other name links its own detail page too, and each row is tinted by the result of the subscriptions it folds — light green = last transfer OK, light orange = configured but never seen (or a mix), light red = one or more last transfers in Error, light blue = surfaced only by the server log. Click a column header to sort.

The UCx column

Column two, and the place the subscriptions themselves live: it lists every use case the FlowID appears under — the UC<n> token from the subscription name prefix, or the one the configuration derives when the name carries none — ordered by number, and each value links that use case’s own subscription detail page. So a flow configured as both a UC1 and a UC4 subscription reads UC1, UC4 on one row, with a link behind each. The Subscription column shows the FlowID itself; it links the subscription detail page when the row is a single subscription, and is plain text when the row folds several — the UCx links reach them individually.

The BL column

The subscription export (subscriptions.json) carries free-form tags; the BL column shows the entry (or entries) starting with BL — the business-line marker. A subscription without such a tag shows a blank cell. Each tag is an entity in the Logical, Partners, Domains, Applications & BL group, and the cell links its detail page.

How it's computed

The roster is the pristine configured snapshot (the base cache before the build appends discovered names), so the list is exactly what FlowManager defines. Everything else is joined from the flow-manager caches: the FlowID from the subscription’s profile pair, the account/login/host from their pair caches, the Logical / Partner / Domain / Application / BL from the derived group caches. The roster is then folded on the FlowID, each cell taking the union of the folded subscriptions’ values and the tint their rolled-up result (any red wins; one shared value carries; anything mixed is orange) — the same rule the derived entities use. A subscription that carries no FlowID keeps a row of its own. No log data is read — only the row tint reflects activity.
