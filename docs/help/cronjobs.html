Cronjobs

What this shows

The polling schedules configured in the FlowManager subscriptions.json export. Every schedule belongs to a UC3 subscription, where SecureTransport is the client: it connects out to the partner’s server on a timer and pulls whatever files are waiting. (Inbound flows — where the partner connects into SecureTransport — are event-driven, not scheduled, so they never appear here.)

The columns

Subscription — the configured subscription name. Protocol — SFTP or FTP, whichever endpoint the schedule polls. Cron expression — the raw schedule as stored in the config. Schedule — that expression translated to plain English.

The cron expression

SecureTransport uses Quartz cron expressions, which have six fields: seconds minutes hours day-of-month month day-of-week. A few examples:

  • 0 0/15 * ? * * — Every 15 minutes.
  • 0 0,30 8-17 ? * MON-FRI — Every 30 minutes on workdays between 08:00 and 17:00.
  • 0 0 4 ? * * — Daily at 04:00.
  • 0 5 * ? * MON-FRI — Every hour at :05 on workdays.

The English translation is computed deterministically from the expression when the site is built — there is no external service and no cost involved, so it is always in sync with the configured schedule.

Notes

Every schedule listed is enabled, and none are configured to skip holidays. The number in the Schedule column is what the timer will actually do; the raw expression is kept alongside it so it can be cross-checked against the FlowManager configuration. Type in the search box to find a subscription; click a column header to sort.

Observed

The Observed column (merged from the former Schedule vs reality page) says when the schedule actually fires: it comes from the server log’s poll lines via the Remote poll report — the median of each day’s first poll, ± one standard deviation, with a rate shown instead for schedules firing more than 3× a day; slots marked · files fall back to the file arrivals (the Punctuality model). A dash means no poll and no File in the loaded logs — the schedule never fires. Polls and Active days count the server-log poll lines and the days the flow showed life. A dark red Observed cell contradicts its schedule: the observed slot sits off the scheduled time, the poll rate is more than 3× off the expected one, or a continuous schedule is only seen firing a few times a day.

Schedules that never complete a poll

The bottom table diagnoses every schedule whose Observed column shows a dash. Almost all of them do fire — their setup lines (“Remote folder / files pattern … evaluated”) appear in the server log right on the scheduled minutes, counted as Poll starts — but the poll then dies before the file listing that would count as a completed poll. What goes wrong shows the dominant failure line: a connection timeout (the partner endpoint is unreachable), an SSH/TLS handshake failure, a password or public-key authentication failure, or a remote listing error such as “No such file” (the login works but the configured remote directory is missing). Connection and listing failures name the subscription in the log; authentication failures name only host and user, so they are matched through the subscription’s configured host and can be shared between flows polling the same host. A row with neither starts nor failure lines never fires at all in the loaded logs.
