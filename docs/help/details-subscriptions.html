Subscription Details

What it shows

One page per subscription, linked from every Subscription cell across the site. Internally the entity is still the Transfer Site; every label reads Subscription.

Sections

  • Banner — when the server log holds an error for this flow after its last transfer: a red ERROR IN SERVER LOG AFTER LAST TRANSFER banner with that log line (date, time, session id) right under it; the line is the verdict.
  • KPI line — rank and share among all subscriptions, failure rate, volume, cadence, processed-transfer performance where a duration is recorded.
  • Pickup information — UC2 pages only (the partner connects in and collects from us); see below.
  • Features — a single-row Partner, Application, Domain or Logical breakdown is folded into a Features row, keeping its link and colour.
  • Activity per day / week / hour / weekday — the day table leads with the Files count.
  • Last error — inline, directly above Last OK transfer, which names the File that last ended OK; see below.
  • Breakdowns — account, login, remote host, protocol, AV scan, security parameters, direction, action-by, mode; Subscription comes first below Activity, Account right under the Incoming/Outgoing connections tables.
  • 10 largest transfers; Server log error — every after-the-last-transfer error line.
  • Whitelisted IPs — when the subscription’s partner carries an AllowIP whitelist (partners.json): the source addresses allowed to connect for it; the whitelist belongs to the partner account, joined via the subscription’s participant. Configuration, not activity: the date filter leaves it unchanged.
  • Last server log messages — at the very bottom: its own 25 most recent lines merged with its 10 most recent Error/Warning lines (a recent problem stays visible when the newest 25 are routine), plus the Error/Warning lines of its 1-to-1 connected entities (typically its one account, login and host) after its last transfer. Deduplicated, newest first, full-period.
  • Any such after-the-last-transfer line, own or connected, raises the red banner ERRORS IN SERVER LOG AFTER LAST TRANSFER – SEE LOG AT BOTTOM OF THIS PAGE.

Server log error rules

  • “After its last transfer” = after the last transfer ended: a File started before the error but delivered after it (a retry that went through) ended OK after the error, so the error does not count and the flow stays green.
  • An error whose session also logged a transfer end (the platform’s “Transfer end logged.” record, any status) does not count: the transfer log has the last word on that session.

Pickup information (UC2)

  • A pickup = a successful SSH logon by the flow’s pickup account in the server log — a connection, not a transfer. The account is shared across its UC2 subscriptions, so the logon figures repeat on each.
  • Logons group into visits; a gap over 30 minutes starts a new one.
  • A visit in which the account only delivered files (its UC4 twin handing files over — inbound SSH rows in the transfer log) is no pickup: those logons sit on Logons that only delivered files (shown only when any) and are excluded from every other figure and from the UC2 status classification.
  • First / Last pickup, Total pickups — the remaining pickup logons. Pickups with actual files — visits that collected at least one file of this subscription. Total files picked up — its collected Files (= the page’s OK figure).
  • Current waiting files, Expired files — its own staged files by outcome, the Waiting/Expired table’s figures.
  • Connection shared with UC4 drop — only on proof: at least one technical SSH connection (the transfer log’s Session ID — one connection, one id) in which the account both delivered and collected a file. A delivery over a separate connection, even seconds apart in the same visit, does not raise it (an SFTP client typically opens a fresh connection per operation).
  • Its value links the UC2 pickup visits analysis, whose Same connection column carries it; the UC4 twin’s page carries the mirror note (“Same connection, both directions”) on the same evidence.
  • Pickup pattern — the typical spacing of the pickup logons (“Daily”, “Every 15 minutes”, …; “Once” for a single visit, the spacing between two when too few for a median; “Irregular” when fewer than six in ten gaps fall within half and double the typical spacing). A partner arriving in bursts is read by how often it visits, not the seconds between a burst’s logons.
  • A partner collecting over CFT/PESIT logs no SSH pickup: its pickups stay 0 while files are still picked up.

Last error

  • Present only when something went wrong on this subscription in the loaded window: the failed file’s own error page spliced in under Last error — <file name> — every leg (status, direction, protocol, size, timing, remote host, Transfer ID), then the server log of the sessions those legs ran on, verbatim, errors red, warnings amber.
  • A link below opens the full error page, which adds the file’s facts table.
  • Error = a failed file or one that expired before the partner collected it; the error page’s title says which. These are the files of the Failed Subscriptions list, which guarantees every subscription’s last error has a page.
  • The other entity pages show the same as a Last error(s) table, one row per connected subscription, each opening that file’s error page.

Rules

  • Every count is in Files, as distinct (subscription, CoreId) pairs: a File touching several subscriptions counts once on each subscription’s page.
  • Server-side connection failures (login/handshake attempts that never became a transfer) are not here — see the server area’s Connection failures report.
  • The account / login / remote host tables are cross-referenced with the FlowManager configuration: every partner configured for this subscription is listed — green = logged data; red = configured, never seen with it (no counts, a link to its never-seen page). Partners logged but not configured are listed too (green).
  • Narrowing the date filter re-tints: a partner without activity in the range turns red instead of being hidden.
  • Every configured name from the FlowManager exports has a page. Background: light brown = seen & in, light blue = seen & out, light gray = seen & both/unknown, light yellow = never seen & in, light orange = never seen & out, light purple = never seen & both/unknown.
  • A never-seen page opens with a “configured, never seen” line, its configured cross-references (all red) and any whitelisted IPs.
  • Configured both ways: every outcome splits into In - Error / In - OK / Out - Error / Out - OK by each file’s own direction; a file without a direction counts in Files and Volume only.
