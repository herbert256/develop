Failed Subscriptions

What it shows

One row per failing subscription — its newest File in error (Failed or Expired) — plus the subscriptions failing in the server log only: together every red subscription, transfer and server alike, the set the home page’s two red tables split. Every File in error is on Failed files.

Views

  • Still failing (default) hides the subscriptions green again (delivered OK since); All keeps them. Each view is its own page (bookmarkable).
  • Outcome Failed or Expired — the site-wide Error rule; an Expired row (a UC2 copy the retention sweep deleted before pickup) reads Expired (not collected).

Columns

  • Environment — the site the row comes from: A Acceptance, P Production (S the sample estate) — so rows copied or exported from both sites stay apart.
  • Subscription — the file’s flow.
  • Date/time — the first leg’s start; server-log row: the server evidence stamp (its last File when none).
  • Reason — the first classifying error line of the file’s server-log section, in the home page’s red-worklist vocabulary (Connection failures, Route stopped, Wrong server fingerprint, …); for a red row the home page’s Reason.
    • One-legged: a single-leg file naming nothing recognisable — arrival without delivery is the failure. A single-leg file whose only evidence would read Unknown error (a bare error end-of-transfer record) reads One-legged too.
    • No own error page: the reason of the newest paged file of the same Subscription + leg-count.
    • Multi-leg, no logged error: the last leg’s raw status (Failed Subtransmission). Blank only when no rule applies.
    • Server-log row: the classified newest server error line, else its Subscriptions-in-boxes box.
  • Last green day — the newest day that ended on an OK File; never for a flow that never delivered. Days red — from the first failure of the current run to the data window’s last day. Failures in a row — the consecutive Files in error. Blank for a flow neither rule lists (a server-log-only red).
  • CoreID / SessionID — the id of the last error. Failed File row: its CoreId, linking SecureTransport File Tracking. Server-log row: the session id of the server-log error line the red verdict rests on (the connection its error page shows) — never a transfer id; blank when the log names no session for it.

Rules

  • Row colour = the subscription’s result, not the file’s: red = newest File an error, green = delivered OK since (All filter only).
  • Source: the logical-transfer cache (one row per CoreId), outcome Failed, newest first; Subscription view = first row per subscription; Still failing drops the greens. Deduped views catalogue failure shapes, not counts.
  • A server-log row is red without a failed File: a server error after its last delivery, a deploy mistake (‘Receive File As’ field not set) or an authentication failure attributed to the flow. Identical on every view.
  • Related: the Top view and Repeat failures for volumes, Failure heatmap for the shape over time, Episodes for outages; this page explains one file.

The error page

  • Any cell of a row (gaps too) opens the file’s own page. Pages exist for every Subscription-view row, the newest failure of every Subscription + leg-count combination, and a subscription’s newest 10 failures per day in the File search windows.
  • An older row of a busy flow (All views) has none — its Subscription cell links the detail page, the rest is plain.
  • Titled by the subscription. Facts: file name, CoreId (for Cloud support; also the page address), date/time, subscription, remote host, account — tinted, linked to their detail pages; a bare-IP host stays plain.
  • Legs: every leg’s status, direction, protocol, size, timing, remote host, Transfer ID — every parse-cache record sharing the CoreId, cache order.
  • Server log: every line verbatim (date/time, level, the line with its JSON), one logged line per page line (no wrapping, scrolls sideways), oldest first; Error red, Warning amber.
  • Join by session: the legs’ connection ids, so the whole conversation — handshake, authentication, PESIT dialogue, abort.
  • Join by id: lines naming a transfer ID or the CoreId anywhere, also on other connections — Error while resubmitting transfer with id on the admin session, the route’s post-processing delete AR0086 … transferStatusId= on the route’s session.
  • Neither matching: the Error lines naming the subscription in the failure’s time window, said above the table.
  • A session is a connection, not a file: it mentions every file it carried — a neighbour failing the same second is evidence, not noise.
  • A server-log row opens the flow’s own error page, named by the subscription: facts (subscription, account — linked, tinted) and its newest server-log mentions, Error / Warning tinted, oldest first.
