Waiting Files

What this shows

A UC2 flow is one the partner collects from us. Such a file does not travel in the usual two legs — it has four:

  1. Inbound / PeSIT — the file arrives from the internal CFT
  2. Outbound / routing — internal staging, within seconds of leg 1
  3. Inbound / routing — the file lands in the pickup area
  4. Outbound / SSH — the partner dials in and collects it (later; sometimes repeatedly)

Between legs 3 and 4 the file just sits staged, waiting for the partner. A file whose last leg is the staging one carries the outcome Waiting — arrived and ready, but not collected yet. That is not an error; it may simply mean the partner has not polled since the file arrived. A staged file the partner never collects does not wait forever, though: the nightly File Maintenance retention sweep (around 03:00, ~11 days after staging) deletes it — those files carry the outcome Expired, with the deletion timestamp in the Expired field. An expired file was never delivered and can no longer be collected. Four tables:

  • Waiting now — per subscription — which subscriptions have staged Files nobody collected that are still on disk: how many, oldest and newest staging moment, and how long the oldest has been waiting. Sorted oldest-waiting first — the top rows are the ones to chase.
  • Files waiting the longest — the individual staged Files, oldest first.
  • Expired — deleted before pickup — per subscription, the staged Files the retention sweep removed before any pickup: never delivered.
  • Pickup wait — collected files — for the files that were collected: how long the partner took (median / average / max, and how many were picked up within an hour, within a day, or later).

How it's computed

A logical transfer (all records sharing one CoreId) whose final leg is a successfully processed Inbound routing leg is Waiting. "Waiting for" counts from the staging moment to the dataset's last record — a file may well have been collected right after the export was taken. When a later export contains the collect leg, the file flips to OK (or Error) on the next build automatically.

The deletion of an expired file leaves no trace in the transfer log — the evidence is only the server log's "File Maintenance … finished. Deleted files […]" lines. A build step joins those onto the Waiting files (same account and file name, deletion dated after the staging) and marks the matches Expired. On every report a Waiting file counts as OK (a normal in-window state) and an Expired file counts as Error (never delivered); this page is where the two states are visible individually.

The pickup wait — from the staging leg ending to the first collect leg starting — is excluded from every Duration figure on this site: a UC2 file's Duration is the arrival work (legs 1–3) plus the collect transfer itself, not the hours the partner let it sit. When a partner collects the same file several times, the idle time between collects is excluded too.

Why the date filter is off

Waiting is a state at the end of the data window, not a per-day statistic — narrowing the range would fake "waiting" files that were collected later. The page always shows the full period (like Stale Accounts and Failure Episodes).

How it relates to the other reports

Failure Episodes shows flows that are broken; this page shows flows that are merely uncollected — the delivery side did its work. Transfer Duration benefits from the same split: without it, a UC2 file that sat staged for three days would count as a three-day transfer.

The Staged backlog table reconstructs the day-by-day staged-but-uncollected inventory: a file occupies every day from staging until pickup or deletion, so the curve’s last day equals the Waiting count. Will expire next lists Waiting files staged nine days or more — the retention sweep deletes staged copies after about eleven days, so these are the partners to call today.

The percentile table rolls collected pickups up to the partner (median, p95, max, and near-misses that waited over eight days); the weekly table tracks the median and average wait per staged week for the ten busiest subscriptions — a rising average flags a partner that paused collecting long before files start expiring.
