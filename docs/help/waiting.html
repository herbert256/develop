Waiting Files

What it shows

UC2 files staged for pickup: which subscriptions have Files the partner has not collected, how long they have waited, how fast partners usually collect.

Always the full period (like Failure Episodes and Went quiet): Waiting is a state at the window end, not a per-day statistic; a narrower range would fake “waiting” for files collected later.

Rules

  • A UC2 file (the partner collects from us) has four legs: Inbound/PeSIT from the internal CFT; Outbound/routing (internal staging, seconds later); Inbound/routing into the pickup area; Outbound/SSH, the partner dials in and collects (later, sometimes repeatedly).
  • Waiting = a File whose final leg is a successfully processed Inbound routing leg, staged copy still on disk; not an error, the partner may not have polled yet.
  • Waiting for runs from staging to the dataset’s last record; a later export with the collect leg flips it to OK (or Error) automatically.
  • Expired = the nightly File Maintenance retention sweep (~03:00, ~11 days after staging) deleted the staged copy before any pickup: never delivered, no longer collectable.
  • The deletion leaves no transfer-log trace; bin/expire-files.sh joins the server log’s “File Maintenance … Deleted files” lines (same account and file name, deletion after staging) into the Expired field, _files.tsv col 22.
  • Every report counts Waiting as OK and Expired as Error; only here are they apart.
  • Pickup wait = staging leg end to FIRST collect leg start (repeat collects count once). parse.sh excludes it, and the idle time between repeat collects, from every UC2 Duration figure.
  • Failure Episodes shows broken flows; these are merely uncollected.

Sections

  • Waiting now — per subscription — staged Files still on disk: count, oldest/newest staging moment, longest wait; Collected = its Files that were picked up. Oldest-waiting first: chase the top rows.
  • Files waiting the longest — the 50 oldest staged Files.
  • Expired — deleted before pickup — per subscription, the Files the sweep removed.
  • Pickup wait — collected files — median / average / max; collected within an hour, within a day, or later.
  • Staged backlog — the uncollected inventory per day: a File occupies the days from staging up to (not including) its collect or delete day, so the last day equals the Waiting count.
  • Same-day pickups never sit overnight; a still-Waiting File runs to the window end. Volume = staged bytes in inventory that day; the peak day is named.
  • Will expire next — Waiting Files staged 9+ days against the dataset’s last day; without a pickup within a day or two they expire: call the partner today. Age = the oldest File’s.
  • Percentile table — collected pickups per partner: median, p95 (slow tail), max, Waited over 8 days (near-misses, one pause from Expired).
  • Partner attribution is the site-wide UNION: a File counts for every partner of its subscription plus the host-resolved one, so partner counts can sum past the collected total.
  • Weekly table — median and average wait per staged week (Monday start), the 10 subscriptions with most collected Files, busiest first. A rising average flags a pausing partner before the median moves; never-collected subscriptions are absent.
