An account (a partner in the FlowManager config) talks to us through one or more communication profiles, each defining how one endpoint connects. This page checks the accounts, their login names and their profiles for configuration slips. A profile name is coded <TYPE>_<partner>_<AUTH>: the prefix is the connection type — SCP/SSCP = server (ST connects out to the partner), CCP = client (the partner connects in) — and the suffix is the authentication — PWD = password, KEY = public key. Below, both are checked against each profile’s real type and clientAuthentication, followed by the account & login checks.

Breaking naming rules (1)

An incoming account (the partner connects to us) separates its name parts with -; an outgoing one (we connect to the partner) uses _. The same flow configured both ways therefore appears twice, once in each spelling — DPL-AXINI-AO-IMPRESS inbound and DPL_AXINI-AO_IMPRESS outbound. The separator is read _-primary: _ wins unless splitting on - yields more parts, so an internal hyphen inside one part (AIM-FIN_TREASURY-SP) is not mistaken for the separator. (A NAMING audit only — since the logical-based derivation the partner/domain/application entities no longer come from account names.)

Not clear domain-application-partner (2)

An account is meant to be connected to a logical flow, whose three-part name reads domain_application_partner — ODV_MAIA_AKZO is domain ODV, application MAIA, partner AKZO. These accounts could not be resolved into all three. The check does not re-read any names: it asks the derivation itself what it managed to assign, so a blank column is a value the rest of the site genuinely does not have for that account.

FTP endpoints (2) — insecure

FTP transfers credentials and data in clear text and cannot use a public key, so these are the site’s only insecure profiles. They are also exactly the 2 profiles outside the PWD/KEY naming convention above (their name ends in a partner tag and their clientAuthentication is unset).
