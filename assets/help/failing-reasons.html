Error reasons

What this shows

Every Reason the Failed Subscriptions pages can show, one row each — with how many currently red subscriptions carry it (Count) and the newest occurrence among them (Last). It is the estate’s failure profile at a glance: which fault classes are live right now, and how widespread each one is.

The row set is fixed, not just what happens to occur: the shared classifier vocabulary (Connection failures, PeSIT transfer aborted, Wrong server fingerprint, … — parsed straight from bin/flip-reason.awk, so a new verdict appears here on its own), plus One-legged and the raw last-leg status, plus whatever a server-log row currently carries (a Subscriptions-in-boxes label). A reason with no red subscription stays listed with blank Count and Last — a fault class disappearing from the estate is visible as an emptied row, and one appearing is a new nonzero.

The view buttons

Two button groups above the table pick the view, each combination a page of its own. Subscriptions (the default) counts each flow once — its newest failure’s reason; Errors counts every individual failed File, so one busy flow counts as many times as it failed. Current (the default) keeps to the still-failing estate; History includes the recovered flows — on the Subscriptions unit its drill rows are tinted red (still failing) or green (recovered since). The Errors drills show at most the newest 500 rows per reason and say so; the searchable All views of Failed Subscriptions hold every one.

The counting

Red subscriptions only, one each: the source is the default Failed Subscriptions view — one row per failing subscription, its newest failed File or its server-log verdict — so the Count column sums to the same red total the home page’s two red tables split between them. Green (recovered) flows never count here, whatever their history; for volumes over time use Failure rate.

The drill pages

A nonzero row opens the list of the red subscriptions carrying that reason — each row exactly as the Failed Subscriptions pages list it (Subscription and Date/time), and opening the same error page: the file’s legs and server log, or the server-failing flow’s reddening session.
