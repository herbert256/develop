Shared Concepts

This site is built from two Cloud SecureTransport logs: the transfer log (every file movement) and the server log (the platform's own info/warning/error messages). Every report page links here for the ideas that show up across many of them. If you followed the ? icon from a specific report, its own help page explains that report's own columns and data source — this page only covers what's shared.

The counting unit: Files

The site counts Files — one logical transfer per movement. In the raw transfer log, one file movement produces several rows: an Inbound (partner→ST) leg, an Outbound (ST→CFT) leg, and up to a handful of retries. A File collapses all of them into a single count and outcome: it counts as OK only if its final, last-chronological row processed — so one failed retry followed by a successful one still counts as OK — and its volume counts the file once, not once per leg. A Files count answers "how many files moved," not "how many log lines."

Because the rows of one File can carry different protocols, ciphers, directions, etc., a handful of reports (protocol, direction/action, security parameters, AV scan) only make sense counted per physical row — those are labelled Transfers (one count per physical leg), and their own help page says so explicitly.

Why a Files count is normally lower than raw log lines

One concrete example makes the unit tangible. A job that retrieves 3 files from a partner counts as 3 Files — one per file, regardless of how many rows or sessions it touched. In the raw log, the very same movement is 6 rows (two per file: an Inbound partner→ST leg and an Outbound ST→CFT leg; a retried leg adds more) spread over 4 sessions (one partner↔ST connection carrying all 3 files, plus 3 separate ST↔CFT connections, one per file). For the same population the Files count is never higher than the raw-line count and is normally lower; they are equal when every File in that population has only one logged leg.

The search box

A page whose tables run past 25 rows gets a single Search box at the top, next to the date filter. It filters every table on the page at once, across every visible column, and supports two wildcards — ? matches any single character, * matches any run of characters (for example FE????? or AB*) — plus the keywords and / or / not to combine terms (RABO or SAP matches rows containing either; ABC and XYZ matches rows containing both; ABC and not XYZ matches rows with ABC but without XYZ, and a leading not XYZ excludes any row containing XYZ). A plain space means AND — ABC XYZ is the same as ABC and XYZ, and abc klm xyz matches rows containing all three — unless you type one of the operator words, in which case the query is taken exactly as written (so to search for the literal word "and" give the operator explicitly: abc and and). Your search term is remembered for the browsing session and re-applied when you come back to the same page. A few tables are excluded from the search by design (for example the transfer-patterns table).

The Search page is the one place where the table starts completely empty — it's a single search across every account, subscription, login and remote host the site knows about, and only shows rows once you type something.

The date range (From / To) filter

A table with a date dimension gets a From/To date-range control, with quick-range buttons beside it: All (the full period), Week / 4 weeks / Month (the last 7 or 28 full days, or one calendar month back — a newest day whose collection stopped mid-day never counts), First day / Last day (the oldest and the newest data day), and Previous day / Next day, which step a single-day selection through the data days (enabled only when From equals To, and grayed at the ends of the period). Narrowing it re-aggregates every visible number — counts, Error/OK splits, percentages, volumes — instantly in the browser, with no server round-trip: the underlying per-date figures are embedded in the page when it's built, and the filter just re-sums whatever is now in range. Your chosen range is remembered for the browsing session and shared across an area's reports (so switching from one report to another keeps the same range), but a few dashboards (the Top-view pages) always reset to the full period on load since they're meant to show the whole dataset at a glance.

Some tables show figures that fundamentally can't be re-aggregated by date — a distinct count of entities active over the whole period, for instance. Those carry a small note: "⚠ The date filter does not adjust this table; values cover the full period."

Sorting

Every column header is clickable: the first click sorts the column (numeric columns open with the largest values first, text columns A–Z), a second click reverses it. Your sort is remembered for the browsing session per report — come back to the page later and the table is still sorted the way you left it. Bar columns (the Load/Distribution bars) aren't sortable; range columns like size buckets sort in their natural order, not alphabetically.

Click-to-expand drill-downs

Many Error/OK counts (and a few other cells, like the Seen and Search reports' "Server Log" yes cells) are clickable — drillable cells carry a dotted underline. Clicking one expands a row underneath listing the 10 most recent matching entries — the newest first, always drawn from the full period even when a date range is selected — so you can see actual examples behind a number instead of just the total.

Error vs. OK

A File counts as OK when its final row's status is exactly Processed; every other status (including the various Failed Subtransmission variants) counts as Error. On the per-row reports labelled Transfers, each physical row counts by its own status under the same rule.
