File search

What this shows

Search the transfer logs' Files by file name or CoreId — split into up to six pages so each loads and answers fast (a window holding no files gets no page and no button): 24 hours (the newest full day, plus the partial newest day when one exists), 48 hours (the second full day), Week (the rest of the last seven days), 2 weeks and 3 weeks (a week each further back) and Month (through data day 30). The windows never overlap — a file is on exactly one page. The button row at the top switches between them; files older than 30 data days are on no page. Each page ships at most 100,000 files (newest first); a capped window says so in its intro, and the build report raises a red warning.

Unlike the other search pages, nothing filters while you type: enter a file name or a CoreId (or part of either) and press Search — or Enter. Wildcards ? (one character) and * (any run) work, and several space-separated words must all match. Matches appear newest first, the first 500 shown. Switching to another window re-runs your current search there automatically — the buttons carry the query along, and it also survives a reload.

Each match shows its date and time, subscription, size and CoreId, and the row's colour is its outcome: green = OK (Delivered, or Waiting — staged for a UC2 pickup that has not happened yet), red = Error (Failed, or Expired — a staged file deleted by File Maintenance before pickup). A red row with its own error page — the facts, every transfer leg and the server log behind it, kept for a subscription's newest 10 failures of each day — opens it from anywhere on the row; every other row opens its subscription's detail page.
