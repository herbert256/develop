UC3 status

What this shows

Every configured UC3 subscription — the pull use case, where we connect out to the partner on a schedule and fetch whatever is waiting — in exactly one of six statuses. It is one of a set of four: UC1 status does the same for the flows we push out to the partner, UC2 status for the ones the partner collects from us, and UC4 status for the ones the partner delivers to us. The info boxes above the table give the count per status. One row per subscription:

  • Status — one of six, a complete partition (see below).
  • Subscription — the configured name, linking to its detail page.
  • Files / OK / Error / Last file — the transfer-log history: logical transfers pulled in, split by outcome, and the date of the newest one. All zero on a blue subscription, which by definition has never appeared in the transfer log.
  • Polls / Empty polls — server-log poll results for this subscription, and how many of them found nothing. A working flow polls far more often than it finds files, so a high empty count is normal, not a fault.
  • Problems — server-log lines saying we could not retrieve: a connection failure, or a directory listing that failed.
  • Last log — the newest server-log line of any counted kind, the ones that merely prepare a poll included. It answers "is this flow still running at all", so on a server - error row it can be newer than the failures the drill shows: the flow still polls, it just last failed earlier.

The six statuses

The first three are the transfer-log verdict, read off the subscription's site-wide result colour:

  • ok (green) — its latest File was delivered. The flow is working.
  • error (red) — its latest File failed and it has never once delivered an OK File in the window. Nothing here ever worked, which points at the configuration or a partner side that was never finished rather than at something that broke.
  • ok -> error (red, was green) — its latest File failed, but it has delivered OK Files before: a regression. Something that used to work stopped, so there is a change to find.

The other three split the blue subscriptions — seen in the server log, never once in the transfer log — by what that log says about them. A blue subscription has no transfer history at all, so its poll lines are the only evidence there is:

  • server - no files — its last poll reported zero files found. The connection, the credentials and the remote directory are all fine; there is simply nothing on the other side. No remote files covers these in depth.
  • server - error — the log's latest word is that we could not retrieve: a Connection failure reaching the partner, or an Error occurred while listing files once connected. See No remote dir and Remote polls.
  • server - no result — the poll is only ever prepared: the log carries the "Remote folder of transfer site … evaluated to …" lines that set a poll up, and then neither a result nor an error. The flow starts and says nothing about how it ended.

A seventh status, not seen, exists for a subscription that is neither green, red nor blue — configured, but never observed in either log. Neither environment currently has one, so neither its box nor any row appears; it is there so a subscription can never silently drop out of the table.

How it's computed

The roster is every UC3 name in the FlowManager subscription export, so a subscription appears whether or not it has ever run. Green/red/blue is the site-wide result colour; Files/OK/Error come from the transfer cache (_files.tsv), and the poll signals from the server parse cache.

error vs ok -> error is a per-File question, not a per-day one: right after any OK File the subscription was green, so a red subscription with even one OK File in the window counts as a regression. That is deliberately finer than From green to red, which buckets by whole days and so misses a flow that fails at the end of every day while still delivering within them.

The blue split takes the most recent decisive line — a poll result of zero files, or a failure. It is latest-wins rather than any-failure-wins because most blue subscriptions carry both signals: 27 of acceptance's 71 have empty polls and failures, and for nearly all of them the failures are a 0.1–8% blip on a flow that otherwise polls perfectly well (one polls 8,941 times and fails 24). Counting any failure would call all 27 broken; a threshold would be arbitrary. The newest line is simply where the flow stands now — the same rule the green/red colour itself follows. A poll that did find files decides neither status, so a subscription with nothing else lands in server - no result.

This is a current-state audit, so the date filter does not narrow it. Click a row for its 10 most recent server-log lines — on a server - error row those are the failures, which would otherwise be lost among thousands of routine poll lines.

Why it matters

A UC3 flow fails quietly. A poll that connects and finds nothing looks exactly like a poll that finds nothing because the partner stopped delivering, and neither writes a single line to the transfer log — which is why two thirds of these subscriptions are blue and invisible on every transfer report. Splitting them by what the server log last said turns that silence into three different questions: chase the partner (no files), fix the connection or the path (server - error), or find out why a poll that starts never reports (server - no result). The red pair is the same triage on the flows that do reach the transfer log: ok -> error has a change to find, error probably never worked at all.
