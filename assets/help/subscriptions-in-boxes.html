Subscriptions in boxes

What this shows

One consolidated list of every subscription flagged by any of the eight problem reports, one column per report:

One-legged transfers — the subscription has CoreIds with only ONE leg (an incomplete crossing) and no OK File after the last one: an OK delivery afterwards means the flow recovered, so it is not flagged here even though the report itself still lists the history. From green to red — it used to deliver OK Files but its latest File failed (a regression). Trouble after Success — its last transfer succeeded but the server log shows Errors/Warnings since. Only red — every File it ever produced is an Error; it never worked at all. Waiting — its newest File is staged for pickup and the partner has not collected it yet. Expired — its newest File expired: the staged copy was deleted by the retention sweep before any pickup, so the last thing that happened to this flow is a lost delivery. No Dir — its configured REMOTE directory does not exist: we reach the partner, the listing fails with "No such file", and no transfer is ever started (only still-open cases count — a directory found again later is not flagged). No Files — a UC3 flow that polls faultlessly but has never found a file: the listing succeeds every time and the remote directory is always empty. Failing polls — the UC3 poll itself errors on the server side (the state UC status / UC3 calls “server - error”): the poll never completes, so nothing is listed or collected.

Login errors (in) — a connected login failed the incoming SSH screening (disallowed, unknown key, key failures, locked) with no OK File since; Login errors (out) — we failed to authenticate at the remote host (password, key or certificate policy) with no OK File since. Both follow the unresolved rule: a later successful delivery clears the flag.

Alongside the problem columns the page carries plain status boxes — OK, Seen, Not seen, Error and Server log only: the site-wide result colors and the coverage flag, read from the same sources as the Transfer / Entities views, so those views are their full lists and the figures cannot drift — Seen is the TRANSFER-scope reading (a flow known only from the server log sits in Server log only instead), so Seen, Server log only and Not seen together are always the whole estate.

Each flagged cell names its box and links into the report behind it; where the target page has a search box, the link arrives pre-filtered to the subscription. The table is sorted by name. The boxes at the top are filters: the page opens on the OK box, clicking a box narrows the table to the subscriptions it flags, and the Total box shows all rows again; columns with nothing left to show are hidden. In the problem rows the orange boxes (attention, or not working yet) come before the red ones (failing). Row tint is the subscription's site-wide result color; the name links to its detail page.

How it's computed

The page is assembled from the four reports' own data files at publish time, so it always agrees with what those pages show — with one deliberate refinement: the One-legged flag is recomputed from the transfer cache (the same one-leg condition pirates uses) and kept only when no OK File follows the last one-legged transfer, compared at full timestamp precision. A report that produced no data in this environment simply contributes no rows (its column stays empty).

Reading the combinations

Only red + Trouble after Success together mean a flow that never worked and is still actively logging errors — the hottest candidates. From green to red alone is a fresh regression: something changed recently. One-legged alone often points at attribution or protocol quirks rather than a hard failure — check the report's own explanation.
