Cleanup backlog

What it shows

  • Every cleanup signal merged into one ranked decommission-candidate list, safest class first. Each object appears once, under its safest class, with its evidence. The boxes count the findings per class.

Columns

  • Object — links its detail page. Type — account, subscription, whitelist (an allowing account), partner, login or host.
  • Reason — the class. Evidence — why. Last activity — never, or the last date.
  • Safety — the hint behind the row tint.

Rules

  • Classes in rank order: config-orphan (no subscription references the account), never-any-traffic (a configured subscription with zero Files), unused-whitelist (allowed addresses never seen, per allowing account), no-cron, long-quiet (no activity for 45+ days before the newest log day).
  • no-cron = a subscription of a cron-triggered use case (UC-named, or derived as one) without a cron expression: it can never poll — the Polling Schedule “no cron”.
  • Green — not seen in the loaded logs (“not seen in N day(s) of logs”). A candidate, not a proof: a quarterly or disaster-recovery flow looks the same. With no transfer log loaded nothing is green.
  • Orange — had traffic, server contact only, or a config gap: check before acting.
  • An address is never seen only without a File, a server contact in (an inbound connection line or an SSH logon line from it) or a server-log mention — the Whitelist audit rule.

Tips

  • Whitelist entries paired with no account are on Config hygiene.
