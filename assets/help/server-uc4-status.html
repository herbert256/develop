UC4 status

What this shows

Every configured UC4 subscription — the inbound-delivery use case, where we are the server and the partner connects in and hands us a file — in exactly one of seven statuses. It completes the set: UC1 status for the flows we push out, UC2 status for the ones the partner collects from us, UC3 status for the ones we poll and pull. The info boxes above the table give the count per status. One row per subscription:

  • Status — one of seven, a complete partition (see below).
  • Subscription — the configured name, linking to its detail page.
  • Files / OK / Error / Last file — the transfer-log history: logical transfers received, split by outcome, and the date of the newest one. All blank on a subscription the transfer log has never seen.
  • Logons — successful partner authentications. It counts both the SSH Allowed user line and the successfully authenticated line the other protocols write, so one connection can contribute more than one: read it as activity, not as an exact session count.
  • Arrivals — files the partner actually handed over ("the file … will be submitted for processing").
  • Problems — logon attempts the account whitelist refused.
  • Last log — the newest server-log line of any of those kinds, so it answers "is this partner still knocking at all".

The seven statuses

The first three are the transfer-log verdict, read off the subscription's site-wide result colour:

  • ok (green) — its latest File arrived. The flow is working.
  • error (red) — its latest File failed and it has never once received an OK File in the window. Nothing here ever worked.
  • ok -> error (red, was green) — its latest File failed, but it has received before: a regression. On acceptance this is the larger half of the red rows, unlike UC1, where every failing flow had never worked at all.

Then the blue subscriptions — seen in the server log, never once in the transfer log:

  • server - no files — the partner does log in. It just never sends anything. This is the most useful thing the report says: the flow is configured, the credentials work, the partner reaches us, and no file has ever come. The question is for the partner, not for us.
  • server - error — the partner never got in at all: its only attempts were refused by the account whitelist. Because we are the server in UC4 we cannot fail to reach anyone, so being turned away at the door is the only way a UC4 flow can break before a file exists.
  • server - no result — the server log carries nothing about the subscription either way.

And last, the largest:

  • not seen (orange) — configured, and never observed in either log. Not a failure so much as an open question: a flow set up and never used, or one whose partner side was never finished. On acceptance this is 64 of 142 subscriptions.

How it's computed

The roster is every UC4 name in the FlowManager subscription export, so a subscription appears whether or not it has ever run. Green/red/blue/orange is the site-wide result colour, and Files/OK/Error come from the transfer cache (_files.tsv).

The server signals are account-keyed, not subscription-keyed. A partner connects to an account; the subscription name barely reaches the server log at all (only the PeSIT confirmation of the onward internal leg carries it). So the roster is joined through the account↔subscription cross-reference, which for UC4 is strictly one-to-one in both directions — 142 accounts, 142 subscriptions, none shared and none missing — and every line therefore attributes to exactly one subscription.

error vs ok -> error is a per-File question, not a per-day one: right after any OK File the subscription was green, so a red subscription with even one OK File in the window counts as a regression. That is deliberately finer than From green to red, which buckets by whole days.

How it differs from the others

  • "server - no files" means what it means on UC2, not on UC3. On UC3 we poll and find the remote directory empty; here the partner connects and simply never sends — the same conclusion, nothing arrives, reached from the opposite side.
  • "server - error" is narrower than on UC1 and UC3. Those two have us dialling out, so they can fail to reach the partner. Here we are the one being dialled, so the only pre-file failure is a refusal.
  • "not seen" is first-class, as on UC1 status. UC3 has none of these at all, so its box stays hidden there.

Why it matters

An inbound flow fails silently and asymmetrically: nothing arriving looks exactly the same whether the partner never sent, never connected, or was turned away — and none of the three writes a transfer record. Splitting the blue rows by how far the partner actually got turns that silence into a specific question: chase the partner for the file (no files), fix the whitelist (server - error), or find out why the flow leaves no trace at all (no result). The ok -> error rows are the ones with a change to find; not seen is estate to review rather than an incident.
