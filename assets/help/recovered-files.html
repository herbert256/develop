Retries & resubmissions › Recovered files

What it shows

  • A recovered File carried at least one failed leg and still finished OK. Eight boxes: Recovered Files, Automatic, Manual, their share of all Files, Failed legs healed, and the Subscriptions, Protocols and Days involved.

Columns

  • Per subscription — Recovered = Automatic + Manual; Files = all its Files; Recovered % = the share that needed a retry.
  • Per protocol — the same split, plus Failed legs healed over all Failed legs of that protocol = Healed %, how often a failure there is transient.
  • Per day — Files, Recovered, Automatic, Manual, Share %; only days with a recovery; the Date opens the day page.

Rules

  • Automatic = a later leg delivered it without an operator (a platform retry, or a failed last leg the server log shows ended ok — a bookend-settled File); Manual = one of its legs carries the Resubmitted flag (an operator). They are the Transfer top view’s Recovered Automatic / Manual and the home page’s Cured.
  • Orange File rows elsewhere cover MORE: every OK File with a failed leg (this page) or a resubmitted leg — a resubmitted File that never failed is orange but not Recovered.
  • OK = Processed or Waiting. A File counts on its start day.
  • Per protocol uses the failed leg’s protocol; failed legs on two protocols count under each, while its Total row counts each File once, narrowed dates included.
  • A narrowed date range hides a subscription or protocol with no recovered File in it.

Tips

  • A high Recovered % on a busy flow points at a flaky endpoint that succeeds on the second try. Click a row for its 10 most recent recovered Files.
