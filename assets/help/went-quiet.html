Went quiet

What this shows

Subscriptions that have carried Files and then stopped: every subscription whose most recent File is more than 7 days before the end of the data window. Two columns:

  • Subscription — the configured name, linking to its detail page.
  • Days ago last traffic — how many days before the end of the window its last File was. 8 means it stopped the day after the 7-day threshold; a large number means it has been silent for most of the window.

Rows are ordered newest-quiet first: a flow that stopped 8 days ago is a live question, one that stopped 31 days ago is probably a decommissioning nobody recorded.

What counts as traffic

Every outcome. Processed, Failed, Waiting and Expired all count as activity, because the question here is is anything still happening — not is it working. A flow that fails every single day is noisy, not quiet, and does not appear. A flow that delivered perfectly and then stopped does.

That is deliberately a different question from the health reports, and they answer it in the other direction: Only red and From green to red judge whether the traffic that is flowing is any good, and the UCx status reports give each subscription a single verdict. A subscription can easily be green here and still be listed — green only means its last File was delivered, however long ago that was.

How it's computed

One pass over the logical-transfer cache (_files.tsv): per subscription the last day it carried a File, against the last day present in the data as a whole.

The count is measured from the end of the window, not from today. The site reports on an export, so counting against the wall clock would make every figure drift with how old that export is — a report read on Monday would disagree with the same report read on Friday, without any data changing. The same convention is used by Stale accounts.

A subscription that has never carried a File is not listed: it cannot have gone quiet. Those are configuration that has never run, and the Entities Not seen view is where they live.

Why it matters

A flow that stops is the failure mode no error report can catch, because nothing fails — there is simply nothing there. It usually means one of three things: the partner stopped sending, the source system stopped producing, or the flow was decommissioned and the configuration was never cleaned up. All three are worth knowing, and only the third is harmless.

The per-account equivalent is Stale accounts, which additionally weighs the idle time against each account's own cadence — a daily account silent for 3 days is more alarming than a monthly one silent for 20. This report deliberately uses a flat threshold instead, so the answer to "what stopped?" is one list, not a ranking.

"Days idle" is not measured against today's date — it's measured against the most recent File seen across every account in the data. So this table reflects staleness as of the end of the collected log window, not as of when you're viewing the page; an account idle "10 days" means 10 days before the last record in the export, however long ago that export was taken.

"Median gap" is the account's own typical spacing between its active days — its normal cadence. The idle÷gap ratio compares its current idle time against that cadence: an account that normally transfers daily and has been idle 3 days (ratio 3.0) has missed three of its own cycles and is more alarming than a weekly account idle 5 days (ratio 0.7), which a flat day-count threshold alone would rank the wrong way round. An account seen on only a single day has no gap to measure, shows "-", and sorts last. Idle 7+ days is tinted, as is a ratio of 2 or more (two missed cycles).
