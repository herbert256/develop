Scheduler Overruns

What this shows

A subscription's scheduled task (a polling pickup) is expected to finish before its next scheduled occurrence comes due. When it doesn't, the server logs: The task "…" of account with name: "ACCOUNT" with subscription folder: "/…/FOLDER" is still in progress. Skipping the next scheduled occurrence of this task. Each such line is one polling occurrence dropped because the previous run hadn't finished — a backlog/latency signal that never shows up in the transfer logs, since a skipped poll starts no transfer at all.

How it's computed

Every skip warning is attributed to the account it names and to the subscription (the last folder segment of the logged subscription path). Two tabs show the same skips rolled up per account and per subscription. Account and subscription names are shown as logged (mono, not linked) — the server writes them with underscores and they don't reliably match the transfer detail-page slugs.

Skipped-run counts are additive and re-total under the date filter. Click a row to expand its 10 most recent skip lines.

Why it matters

A chronic overrun means the poll interval is shorter than the actual run time. If the source keeps producing data in the meantime, this can build a growing backlog even though nothing in the transfer logs looks wrong.
