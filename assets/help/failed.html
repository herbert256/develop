Failed Subscriptions

What this shows

The failed Files, newest first — a straight worklist rather than an aggregate. Every other page in this group tells you which subscriptions or which accounts are in trouble; this one names the individual files, so you can look at what actually happened to one of them.

The view buttons

Two button rows below the date fields pick the view; each combination is a page of its own, so a chosen view survives a reload and can be bookmarked.

The first group chooses the rows: All = every failed File (capped at the newest 10,000 — the page says so when the cap bites); Subscription (the default) = each subscription’s newest failed File, one row per subscription.

The second group chooses the flows: Still failing (the default) hides the subscriptions that are green again — they have delivered OK since their failure — so the page reads as the current worklist; All keeps them, turning the page into the full failure history. So the default view is one row per subscription that is failing right now, and an absent subscription means nothing is failing on it.

The file rows are Failed files only. An Expired file — a UC2 copy staged for a pickup that never came — counts as an error site-wide and colours its subscription red, but it is a pickup problem rather than a delivery failure and has its own Expired report.

The server-log rows

A row can also be a subscription failing in the server log only: red without a single failed File — a server-log error after its last delivery, a deploy mistake such as ‘Receive File As’ field not set, or an authentication failure attributed to the flow. Its Date/time is the server evidence stamp (its last File when no stamp exists), its Reason the classified newest server error line, else its Subscriptions-in-boxes box. Like a file row, the whole row opens the flow’s own error page — named by the subscription rather than a CoreId — with a facts table (subscription and account, linked and tinted) and the flow’s newest server-log mentions, Error and Warning lines tinted, oldest first; the detail page is one click further from its facts. These rows appear identically on every view (they are subscription-level facts, red on both filters), so together the file rows and the server rows cover every failing subscription, in transfer and in server alike — the same total the home page’s two red tables split between them.

  • Subscription — the flow the file belongs to.
  • Date/time — the first leg's start; for a server-log-only row, the server evidence stamp.
  • Reason — the fault this file's own drill page shows: the first error line of its server-log section that classifies, in the same vocabulary as the home page's red worklist (Connection failures, Route stopped, Wrong server fingerprint, …). For a red row this is the same Reason the home page gives that flow. A single-leg file whose log names nothing recognisable reads One-legged — the arrival with no delivery is itself the failure. A file without its own error page (possible on the All views) borrows the reason of the newest paged file of its Subscription + leg-count combination — the same failure shape, the closest evidence there is — and a multi-leg file whose sessions logged no error shows its last leg's own raw status (Failed Subtransmission), exactly as the legs table on its page shows it. Blank only when no rule applies.

The row colour

A row carries the colour of its subscription — the same result colour the entity pages and the Entities views give it, not a property of the file in the row. Red means that flow is still failing: its newest File is an error. Green means it has delivered OK since. On the Still failing views the greens are filtered out, so those pages are effectively all red; the All filter shows both, a green row being a failure that has since been overtaken by a recovery.

The drill page

Clicking anywhere on a row opens that file's own page — every cell, the Subscription name included, and the gaps between them. There is no cell that quietly goes somewhere else. The subscription's own detail page is still one click further on: the error page names it, linked, in its facts table. Error pages exist for every row of the Subscription views (and for the newest failure of every Subscription + leg-count combination), and for a subscription's newest 10 failures of each day in the File search windows; on the All views an older row of a busy flow has none — its Subscription cell then links the detail page and the rest of the row is plain.

The drill page is titled by the subscription, and opens with a small facts table: the file name, the CoreId (the value to quote to Cloud support — it is also the page’s address), the date and time, and then the subscription, remote host and account the file belonged to. Those last three carry the entity’s own result colour and link to its detail page, so the page is a junction: from one failed file to every entity around it. A remote host that is a bare IP address has no entity of its own and stays plain.

Below that, the table of every leg with its status, direction, protocol, size, timing, remote host and Transfer ID. That is where a retry storm becomes readable: the same endpoint refusing eight times in ninety seconds looks very different from one leg that timed out once.

How it's computed

The lists come from the logical-transfer cache — one row per CoreId — filtered to outcome = Failed and sorted newest first. The Subscription view keeps the first row of each subscription, the All view everything; the Still-failing filter then drops the rows whose subscription's result colour is green. Because the deduped views list a shape once however often it failed, they are a catalog of failure shapes and not a count of failures: for volume, use Failure rate and Repeat failures. The drill pages come from the parse cache, every record sharing that CoreId, in cache order.

Expired files are not part of the selection, nor of the guarantee. An expired file is a different kind of failure — a UC2 file staged for a pickup that never came — and it has its own Expired report in this group, so listing them here would double-count the same problem.

How it relates to the other pages

Failure rate and Failure heatmap give the shape of the failures over time and per entity; Episodes groups them into outages; Repeat failures looks at what gets retried. Use this page when you have one file to explain rather than a pattern to find.

The server log below the legs

The second table on an error page is the server log of the failure — every line, not a sample: date and time, level, and the line itself exactly as it was logged, JSON payloads and all, so nothing is paraphrased away. One logged line is one line on the page — nothing wraps, so a long payload runs off to the right and the table scrolls sideways rather than folding into a paragraph. Lines are in the order they happened, oldest first; Error lines are tinted red and Warnings amber.

Two joins fill it, neither of them shown as a column:

  • By session — the server cache records the connection id of every line, and the transfer legs record theirs, so the table holds the whole conversation each leg took part in: the SSH handshake, the authentication, the PESIT dialogue, the abort and everything in between. This is usually the bulk of it.
  • By id — lines naming one of the File’s transfer IDs (or its CoreId) anywhere in the message. Most such lines are on the file’s own session anyway; the ones only this join reaches were logged on a different connection: Error while resubmitting transfer with id ‘…’ comes in on the admin session the resubmit was requested from, and the route’s post-processing delete (AR0086 … transferStatusId=) on the route’s own session. So a resubmit attempt that failed shows on the page even though no leg of the file carried that connection.

For a file neither join matched, the page falls back to the Error lines naming the subscription inside the failure’s time window, and says so above the table.

Note that a session is a connection, not a file: when one connection carried several files, its lines mention all of them. That is the point — a neighbouring file failing the same second is evidence, not noise — but it does mean not every line on the page is about this file.
