Subscription Details

What this shows

The per-subscription detail page — one real page per subscription (linked from every Subscription cell across the site). Internally this entity is still called the Transfer Site, but every label reads Subscription. It opens with a KPI line, then Activity per day/week/hour/weekday, a breakdown of every other dimension the subscription's transfers touch (account, login, remote host, protocol, AV scan, security parameters, direction, action-by, mode), and the 10 largest transfers seen for it.

When the subscription's partner carries an AllowIP whitelist (partners.json), a Whitelisted IPs table at the bottom lists the source addresses allowed to connect for this subscription — the whitelist belongs to the partner account, joined here via the subscription's participant. Configuration, not activity: the date filter leaves it unchanged.

At the very bottom a Last server log messages table shows the tail of the server log for this subscription: its own 25 most-recent lines merged with its 10 most-recent Error/Warning lines, so a recent problem stays visible even when the newest 25 are routine. It also folds in the Error/Warning messages of the subscription's 1-to-1 connected entities (typically its one account, one login and one host) that occurred after this subscription's last transfer. Deduplicated, newest first, full-period. When any such after-the-last-transfer Error/Warning exists (own or connected), a red banner appears at the top of the page: "ERRORS IN SERVER LOG AFTER LAST TRANSFER – SEE LOG AT BOTTOM OF THIS PAGE".

The account / login / remote host tables are cross-referenced against the FlowManager configuration: every partner configured for this subscription is listed, whether it appears in the logs or not. Green rows have logged data; red rows are configured but never seen with it — they carry no counts but do link to that name's own (never-seen) detail page. Partners logged without being configured are listed too (green). Narrowing the date filter re-tints the rows: a partner with no activity in the selected range turns red instead of being hidden.

The "Pickup information" table (UC2 pages)

A UC2 subscription (the partner connects in and collects from us) opens with a Pickup information table. A pickup is a successful SSH logon by the flow’s pickup account in the server log — a connection, not a transfer — and the account is shared across its UC2 subscriptions, so the logon figures repeat on each of them. The logons group into visits (a gap of more than 30 minutes starts a new one); a visit in which the account only delivered files — its UC4 twin flow handing files over, visible as inbound SSH rows in the transfer log — is not a pickup: those logons appear on the Logons that only delivered files row (present only when there are any) and are excluded from every other figure and from the UC2 status classification. First / Last pickup and Total pickups count the remaining pickup logons; Pickups with actual files counts the visits that collected at least one file of this subscription; Total files picked up counts this subscription’s collected Files (it matches the page’s OK figure). Current waiting files and Expired files are this flow’s own staged files by outcome — the same figures as the Waiting/Expired table. The optional Connection shared with UC4 drop row appears only on same-connection proof: at least one technical SSH connection (the transfer log’s Session ID — one connection, one id) in which the account both delivered and collected a file. A delivery over a separate connection — even seconds apart, in the same visit — does not raise it, because an SFTP client typically opens a fresh connection per operation. The value links the UC2 pickup visits analysis, whose Same connection column carries this figure. The mirror note appears on the UC4 twin's page ("Same connection, both directions") on the same session-proven evidence. Pickup pattern reads the typical spacing of the pickup logons (“Daily”, “Every 15 minutes”, …; “Once” for a single visit, and the spacing between two, when there are too few visits for a median; “Irregular” when the gaps have no rhythm, fewer than six in ten falling within half and double the typical spacing): a partner arriving in short bursts of connections is read by how often it visits, not by the seconds between the burst’s logons. A partner collecting over CFT/PESIT logs no SSH pickup at all, so its pickups stay 0 while files are still picked up.

The "Last error" section

When anything has gone wrong on this subscription, the page carries its most recent failure inline, directly above the Last OK transfer section: the content of the failed file’s own error page, under the heading Last error — <file name>. First every leg the file took (status, direction, protocol, size, timing, remote host, Transfer ID), then the server log of the failure — the lines of the sessions those legs ran on, verbatim, errors tinted red and warnings amber. A link below opens the full error page, which adds the file’s facts table. No section means nothing has gone wrong on this flow, in the loaded window.

Error here is what it is everywhere on the site: a failed file or one that expired before the partner collected it. The error page says which in its title. These are the same files the Failed Subscriptions list holds — that page guarantees every subscription’s last error has a page, which is what lets this section splice it in. On the other entity pages (accounts, logins, hosts, partners, applications, domains) the same information appears as a Last error(s) table, one row per connected subscription, each row opening that file’s error page.

Direction, page colors and never-seen pages

Every configured name from the FlowManager exports has a page — seen in the logs or not — and the page background color says the same at a glance: light brown = seen & in, light blue = seen & out, light gray = seen & both/unknown, light yellow = never seen & in, light orange = never seen & out, light purple = never seen & both/unknown. A never-seen page opens with a "configured, never seen" line and shows the configured cross-references (all red) and any whitelisted IPs.

An entity configured both ways splits every outcome into four columns — In - Error / In - OK / Out - Error / Out - OK — by each file's own direction; a file with no direction of its own counts in Files and Volume only.

When a page carries both green (logged) and red (configured-only) rows, the tint tells them apart at a glance. The Activity per day table leads with the Files count; the Subscription breakdown comes first below it, and the Account breakdown renders right under the Incoming/Outgoing connections tables.

How it's computed

The KPI line adds this subscription's rank and share among all subscriptions, failure rate, volume, and cadence, plus processed-transfer performance where a duration is recorded. Every count on the page is in Files, counted as distinct (subscription, CoreId) pairs — a File touching several subscriptions counts once on each subscription's page. Server-side connection failures (login/handshake attempts that never became a transfer) are not on this page — see the server area's Connection failures report.

A Partner, Application, Domain or Logical breakdown holding exactly one row is folded away: the name appears as a row in the Features table instead, keeping its link and colour.
