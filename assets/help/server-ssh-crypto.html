SSH/TLS Crypto

What it shows

The cryptography really in live use, from the “Connection security parameters” line every authenticated connection logs (cipher, key exchange, MAC, public-key algorithm), with the weak algorithms flagged, the server’s own deprecated-parameter warnings, session lifecycle problems and the protocol/credential hygiene signals. None of it is visible from the transfer log.

Sections

  • Cipher suites / Key exchange / MAC / Public key — per algorithm: negotiations, share within the table, Assessment OK or Weak (red): CBC/3DES/RC4 ciphers, SHA-1-based key exchange or MAC, ssh-rsa/ssh-dss keys (they sign with SHA-1).
  • Negotiations by protocol — the SSH/PeSIT/HTTPS/FTPS split.
  • Deprecated parameters — the “Insecure or deprecated SSH connection parameter used” warnings, with the account, subscription and remote host as logged; a name matching a known transfer-log entity links to its detail page.
  • Algorithm negotiation failures — outbound SSH connections that died before authentication because no common algorithm exists, with the remote software banner.
  • PeSIT TLS adoption — the PESITD “Establishing PeSIT SSL connection with host …, using cipher suite: …” lines: the internal ST–CFT link over TLS. The first line dates the moment it went encrypted (before it, the link ran in the clear); Per-week is the ramp, one line per calendar week dated by its Monday.
  • Session lifecycle problems — sessions referenced after teardown, streams aborted mid-transfer.
  • Hygiene signals — connection- and credential-level problems, five kinds, each from one distinct message so they never overlap; Level is the actual log level (CONFIG_PASSWD Error, disconnects Warning, the rest Info):
    • ASCII transfer fallback — “ASCII transfers are not supported for the current ssh client version. Binary transfer mode will be used.”
    • FTPS connection establishment failed — “Trying to establish an FTPS connection with protocols […] failed.”
    • CONFIG_PASSWD read error — “Error reading CONFIG_PASSWD state variable”: a stored credential could not be read.
    • Certificate chain error — “Error in certificate chain for Subject DN:CN=…”: a trust-chain problem for one key.
    • Disconnect error — “Error during disconnect operation: …”: an abrupt teardown, e.g. a broken pipe.
  • Certificate chain errors by CN — the PUBKEY_/PRIVKEY_ key names: exactly which key’s trust chain is broken.

Rules

  • Both shapes of the parameters line are parsed: cipher suite: X; Key exchange: Y; HMAC: Z; Public Key: W (SSH/PeSIT/HTTPS) and cipher: X, MAC: Z, Key Exchange: Y, Public Key: W (FTPS/PeSIT-initiated).
  • A TLS 1.3 connection (HTTPS, PeSIT/FTPS over TLS) logs only a cipher suite — key exchange, MAC and signature are folded into it. So Cipher suites covers every negotiation; Key exchange, MAC and Public key only the SSH/SFTP connections that itemize them — the intro states both counts.
  • No hygiene signal stops a well-behaved transfer by itself; each is a latent config or trust problem that turns into a hard failure or a security gap.
  • All tables re-total under the date filter; occurrences are additive.
