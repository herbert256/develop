SSH/TLS Crypto

What this shows

Every authenticated connection logs a "Connection security parameters" line naming the cipher, key exchange, MAC and public-key algorithm it actually negotiated. This report inventories what cryptography is really in live use, and flags the weak/deprecated algorithms still showing up: CBC/3DES/RC4 ciphers, SHA-1-based key exchange or MAC, and ssh-rsa/ssh-dss host keys (which sign with SHA-1). It also lists the server's own warnings when it flags a connection parameter as insecure or deprecated. None of this is visible from the transfer logs.

The two tables at the bottom collect the protocol & credential hygiene signals: connection- and credential-level problems that aren't crypto-algorithm posture and aren't a specific transfer failure. Five signals are classified from the server messages:

  • ASCII transfer fallback — "ASCII transfers are not supported for the current ssh client version. Binary transfer mode will be used." (a client asked for ASCII mode; the server fell back to binary).
  • FTPS connection establishment failed — "Trying to establish an FTPS connection with protocols […] failed."
  • CONFIG_PASSWD read error — "Error reading CONFIG_PASSWD state variable" (a stored credential couldn't be read).
  • Certificate chain error — "Error in certificate chain for Subject DN:CN=…" (a trust-chain problem for a specific key).
  • Disconnect error — "Error during disconnect operation: …" (an abrupt/broken teardown, e.g. a broken pipe).

The last table breaks the certificate-chain errors down by their CN subject — the PUBKEY_/PRIVKEY_ key names — which is the actionable part: it tells you exactly which key's trust chain is broken. None of these hygiene signals stop a well-behaved transfer on their own, but each is a latent config or trust problem that will eventually turn into a hard failure or a security gap.

How it's computed

The security-parameters line comes in two shapes and both are parsed: an SSH/PeSIT/HTTPS-style line (cipher suite: X; Key exchange: Y; HMAC: Z; Public Key: W) and an FTPS/PeSIT-initiated style (cipher: X, MAC: Z, Key Exchange: Y, Public Key: W). A separate table covers the "Insecure or deprecated SSH connection parameter used" warnings, shown with the account, subscription and remote host that triggered them, as logged.

Each hygiene signal is matched from a distinct, specific message, so the categories don't overlap. The Level column reflects the actual log level (CONFIG_PASSWD is logged at Error, disconnects at Warning, the rest at Info). Occurrences are additive and re-total under the date filter.

A TLS 1.3 connection (HTTPS, and PeSIT/FTPS over TLS) logs only a cipher suite — key exchange, MAC and signature are folded into that suite and never broken out separately. So the Cipher suites table covers every negotiation, while the Key exchange, MAC and Public-key tables only cover the smaller set of SSH/SFTP connections that itemize those fields separately — the report's intro states both counts so the difference is explicit.

Reading the tables

Each algorithm table shows negotiation count, share within that table, and an Assessment of OK or Weak (tinted red). The Negotiations by protocol table gives the SSH/PeSIT/HTTPS/FTPS split. All tables re-total under the date filter; click a row to expand its 10 most recent log lines.

Algorithm negotiation failures shows outbound SSH connections that died before authentication because no common algorithm exists, with the remote software banner. PeSIT TLS adoption dates the moment the internal ST–CFT PeSIT link went encrypted, with a per-week ramp.
