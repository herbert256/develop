No remote dir

What this shows

Subscriptions whose configured remote directory does not exist. We reach the partner, authenticate and ask for a directory listing, and the partner answers No such file:

Error occurred while listing files from partner UC1_AB_DIRIGENT_PMM_QUION_…_PWD defined in account AB_DIRIGENT_PROMMISE. No such file: '/SSIS/Mortgages/Data/QUION/Monthly': No such file.

The connection itself is healthy — this is a configuration fault on one side of the flow: the path was renamed or never created, the partner moved it, or the account is chrooted somewhere else so the absolute path resolves elsewhere. A subscription appears once, newest failure first: Last is its most recent failed listing, and every directory it was rejected on — often several spellings of the same path, a good sign someone was guessing — is stacked in the Remote directory cell, newest first (click a long cell to expand it).

The Per day table shows when it happened and how many subscriptions were affected each day: a short burst is usually someone reconfiguring, a flat line every day is a flow that has been dead for the whole window.

How it's computed

From the TM error above, with or without its Error during transfer operation: prefix. Only the No such file reason counts here; other listing failures (Permission denied, …) are counted per subscription by Remote Polls, which also covers the polls that do list a directory but find it empty.

Only open problems are listed. A row is dropped when the flow recovered after that row's last error, on either proof: an OK File in the transfer cache, or — on a UC3 (pull) subscription — a later Applying the search pattern '*' for transfer site '<SITE>': 0 file(s) were found of which 0 matched the pattern. line for the same site. That second proof matters because a poll that finds nothing downloads nothing: it leaves no transfer record at all, so a UC3 flow whose directory came back but stays empty would otherwise look permanently broken. Either way the directory was found again, so the path has been fixed and there is nothing left to act on. The intro says how many directories were suppressed that way, and every figure on the page — totals, per-day table, subscription and directory counts — is over the surviving rows, so what you read is what is still broken at the end of the window. (OK is the site-wide rule, any outcome that is not Failed or Expired; on these pull flows that is exactly Processed.)

The subscription is the logged site truncated at its _SCP_ suffix, and the account is taken from the message's "defined in account" clause; both link to their detail page when the name resolves. The remote directory is the path the partner rejected, shown exactly as logged — including odd separators, which are often the cause. Error counts are additive, so a date-filtered range re-totals them. Click a row to expand its 10 most recent log lines.

Why it matters

A failed listing starts no transfer, so none of this reaches the transfer logs: the flow simply looks silent there, indistinguishable from a partner with nothing to send. That makes this one of the few places where a broken configuration is visible at all — and it is cheap to fix once you can see which directory the partner actually rejected. Compare with Remote Polls (the folder is right but always empty) and Connection failures (we never reach the partner at all).
