UC2 status

What this shows

Every UC2 (partner collects from us) pickup flow, classified into five statuses — the info boxes above the table give the count for each. It is one of a set of four: UC1 status does the same for the flows we push out to the partner, UC3 status for the ones we poll and pull, and UC4 status for the ones the partner delivers to us. One row per subscription:

  • Subscription — the "collect from us" subscription (the account's primary movement-out flow, else its configured subscription), linking to its detail page. The flow is keyed internally by the account that owns the pickup folder — that is the token the server log lines carry — but the account is not a column: one account owns one UC2 subscription here, so the name would only repeat what the subscription already says. The account detail page is one click away, through the subscription.
  • Expired — how many files File Maintenance deleted from the account's folder (per file, from "File Maintenance … finished. Deleted files [ … ]").
  • First / Last arrived — when the app first and last staged a file for the flow, from the transfer log. This is the actionable timeline: a file "arrived" long ago and is still not collected.
  • Pickups / Last pickup — successful partner logons ("Allowed user … from address …"). Zero means the partner never connected over SSH to collect.
  • Status — one of five, a complete partition of the UC2 flows: Never collected (red): files expired, zero successful pickups — nobody collected. No files (amber): the partner logs in to collect (pickups > 0) but the app never staged a single file — a dormant or broken source side. Both (green): the partner picks up and the odd file still expired — both outcomes on the one flow. OK (green): files staged and collected, none expired — healthy. Nothing (plain): no pickup and no expiry — a quiet flow, or one whose partner collects over CFT (which logs no SSH pickup).

How it's computed

Expiry (File Maintenance deletes) and SSH pickups come from the server log, keyed on the NAME@FEnnn account token; the subscription and the arrival dates come from the transfer _files.tsv cache (files this subscription staged, movement out). Detection is deliberately on the retention delete, not on arrival. Arrival-based detection ("files staged AND no SSH pickup") flags 101 of 113 pickup subscriptions, because most partners collect over CFT/PESIT and never log an SSH pickup — so arrival alone can't tell collected from uncollected. A file the sweep actually deleted, by contrast, was collected by nobody: a direct-SFTP pickup would log the connection, and a CFT pickup would have removed the file before it could expire. The arrival date is shown anyway, as the timeline. This is a current-state audit — not adjusted by the date filter; click a row for the account's 10 most recent maintenance-delete messages. A row is a UC2 flow (an account with a UC2 subscription). The No files and OK statuses need the positive SSH signal, so they only distinguish SFTP-collecting partners; a CFT-collecting partner with no expiry lands in Nothing. No-files and OK rows drill to the partner's recent pickup logons.

Why it matters

A configured pickup flow that produces files nobody collects is a silent failure — nothing errors, the file just expires. It usually means the partner side is wrong: they connect over a different channel, their credentials or schedule changed, or they are refused at the door — the Logon report's Disallowed column shows the whitelist-rejected attempts. A high Files expired with a recent Last arrived and no pickups is a live flow worth chasing with the partner; a one-off expiry on an otherwise-collecting account is normal.
