Inbound Connections

What this shows

Who connects in to SecureTransport, over which protocol, from where — from the "User with login name "…", associated with account "…", had initiated a connection over SSH|PESIT|FTP. Remote address: …" lines the server logs for every inbound connection. Five tables:

  • Connections by protocol — the volume per protocol. This is the only place FTP and PeSIT inbound connection volume exists on this site.
  • Connections per day — the daily SSH / PESIT / FTP trend. A protocol falling silent, or a sudden spike, shows here first.
  • By account — connections per account, with its protocol mix and the distinct source addresses seen. An account known from the transfer logs links to its detail page.
  • By source address — the partners' SOURCE addresses (what actually connects in — the address a whitelist allows), top 50 by connections.
  • Whitelist policy usage — which Login Restriction Policy the screening actually matched, from the "Allowed user … corresponding policy name '…'" lines.

How it's computed

One count per connection line — this is connection volume, before any authentication or transfer happens. The distinct-count columns (Addresses per account, Accounts per address/policy) cover the whole period and do not re-aggregate under the date filter; the connection counts do. Click a row for its 10 most recent connection lines.

How it relates to the other connection reports

Three reports look at inbound sessions from different angles: Logon is the screening funnel (allowed / disallowed / no-account / lockouts per login), Auth Activity counts successful SSH authentications, and this report counts raw connections — every protocol, before and regardless of authentication. Comparing them is informative: many connections with few authentications means clients connecting and failing (or probing); connections from an address the whitelist table doesn't know is worth a look.

Host-key mismatches lists every presented-vs-expected SSH fingerprint pair from the “Wrong server fingerprint” warnings — one presented key against many stored keys means a server-side key rotation (or something worth a closer look). Test outcomes breaks the explicit test connections down by their error reason.
