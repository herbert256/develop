Accounts (analyses)

What this shows

The configured accounts checked against their communication profiles — one profile per endpoint, defining how that connection is made. The page is a configuration audit, not a traffic report: it reads partners.json only, so a finding here is a config slip whether or not any file ever moved.

A profile name is coded <TYPE>_<partner>_<AUTH>. The prefix is the connection type — SCP/SSCP = server (SecureTransport connects out to the partner), CCP = client (the partner connects in to us) — and the suffix is the authentication — PWD = password, KEY = public key. Both halves are checked against what the profile actually declares (type and clientAuthentication), so a name promising one thing while the profile does another shows up as a mismatch.

Below the naming checks come the account-level ones: accounts carrying more than one communication profile (normally an account has exactly one endpoint), and profiles whose login and loginName disagree — the two should be identical on client profiles.

How it's computed

Straight from the FlowManager export input/<env>/flow-manager/partners.json (via jq), not from any log. Every table lists the offending objects by name, so each row is directly actionable in FlowManager.
